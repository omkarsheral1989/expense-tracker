# OwnLedger

Client-only, installable PWA for personal and shared (group) expenses. All data is stored on the device. Group data is shared through Google Drive. No backend.

Details: @docs/PRD.md (features, pages, open questions) and @docs/ADR.md (architecture decisions and why).

## Stack
- React 19 + TypeScript + Vite, React Compiler enabled
- Ant Design 6 (`antd`), `react-router`, `react-day-picker` (the date calendar only, ADR-033), `recharts` (every chart, ADR-064), `@tabler/icons-react` (the app's own icons through `src/components/Icon`, ADR-066; Ant Design's built-in icons stay inside its components)
- PGlite (Postgres in the browser, IndexedDB storage) + Drizzle ORM, `drizzle-kit` for migrations
- `idb` for the receipt photo store (IndexedDB), `zod` for validation, `zustand` for app state
- `@react-oauth/google` for sign-in, Google Drive REST API via `fetch`
- `vite-plugin-pwa`, `vitest` + `@testing-library/react`, `papaparse`
- Package manager: `bun`

## Commands
- `bun run dev` start the dev server (the app is at `http://localhost:5173/ownledger/`, ADR-032)
- `bun run build` type-check and build
- `bun run lint` lint
- `bun run test` run tests (Vitest, through `scripts/run-tests.mjs`, which stops a run that takes more than 5 minutes; a normal run takes about 30 seconds)
- `bun run preview` serve the production build at `http://localhost:4173/ownledger/` (the service worker only runs there)
- `bun run deploy:pages` build and copy into the `omkarsheral1989.github.io` repository (never commits or pushes; see ADR-032)

## Rules
- **Folder structure:** each page is `src/pages/<name>/index.tsx` (the entry point, a named export such as `WelcomePage`). Its components live in `src/pages/<name>/components/<Component>/index.tsx`, one folder per component, nested by use: a component used only by one parent sits inside that parent's folder (`components/Hero/SignInButton/index.tsx`). Anything shared by several components lives at their lowest common parent (`components/Section`). A component's own files sit beside its `index.tsx`: copy and data in `content.ts(x)` (`Faq/content.tsx`), styling constants such as colors in `style.ts` (`InstallCard/style.ts`). Constants used by several components sit beside the page entry (`constants.ts`). Import a component folder without a file name (`'../Section'`).
  Shared code stays outside pages, one folder per item, each with an `index.ts(x)` entry:
  - Common components: `src/components/<Component>/index.tsx` (`RequireAuth`).
  - Common zustand stores: `src/stores/<useXStore>/index.ts` (`useAuthStore`).
  - Common hooks: `src/hooks/<useX>/index.ts` (`useSignIn`).
  - Services: `src/services/<xService>/index.ts`, exporting one object. They wrap an outside API (`googleProfileService`), hold rules and business logic (`currencyService`), or read and write the database (`groupService`). A service that touches the database takes `db` (from `getDb()`) as its first argument, validates its input with a zod schema in `schemas.ts`, and returns problems with the input as field errors rather than throwing; only unexpected failures throw.
  - Database code: `src/db` (schema, migrations, client, session and tab lock, with `constants.ts` and `types.ts` beside them; tests in `src/db/__tests__`). The hook that opens it is `src/hooks/useDatabaseSession`.
  - Other shared code: `src/pwa` (platform detection), `src/theme` (shared style constants: `radius.ts`, `groupTypeColors.ts`, `categoryColors.ts`, `balanceColors.ts`, `memberColors.ts`).
  - App-level files stay in `src`: `main.tsx`, `App.tsx`, `config.ts`, `env.d.ts`, `index.css`, and `routes.ts` (every address of the app in the `ROUTES` object; never spell a path out in a page, and never put the `/ownledger/` prefix in it: the router's `basename` adds it).
  - Hosting and tooling files sit outside `src`: `deploy/404.html` (the single-page-app fallback for GitHub Pages), `scripts/deploy-pages.sh` and `scripts/run-tests.mjs`.
  - Test helpers live in `src/testing`: the shared setup (`setup.ts`, loaded by Vitest before every test), `setUpTestDatabase()` for an in-memory database, `renderPage()` to render a page inside the theme and a router, `expenses.ts` (`addTestExpense`, `addTestSettlement`, `expenseInput`, `personIdOf`) to create valid expenses and payments between members, and `groups.ts` (`createTestGroup`, `addTestPerson`, `memberIdsOf`, `ensurePersonId`) to create groups and people, and `ids.ts` (`personIdForEmail`): the person id of a test user, which `renderPage` gives a page as the current user (from the auth store's profile, or the guest flag) and the helpers use when they save that email. `logs.ts` (`captureLogs()`: read the log lines a test caused, ADR-048) and `memoryPglite.ts` (in-memory PGlite for whole-app tests in `src/__tests__`, ADR-049). `fakeDrive.ts` is an in-memory Google Drive for backup and sync tests (ADR-044): `createFakeDriveWorld()` for several users (`clientFor(email)`, with sharing), `createFakeDrive()` for one. Tests that touch the photo store import `fake-indexeddb/auto`. `recharts.tsx` (`withFixedSize`) is for a test file's `vi.mock('recharts', …)`: it gives a chart a fixed size and turns the pie's animation off, since jsdom has no layout (ADR-064). See ADR-029.
  - Every component and hook is its own folder, even the small ones (`components/GoogleLogo`, `components/ThemeProvider`, `components/PwaUpdatePrompt`, `hooks/useInstall`).
  An item's own files sit beside its `index.ts`: types in `types.ts`, constants in `constants.ts`, zod schemas in `schemas.ts`, small pure helper functions in `utils.ts` (tested in `__tests__/utils.test.ts`). Tests go in a `__tests__` folder beside the code they test (`useSyncSessionAcrossTabs/__tests__/index.test.ts`). Code used by only one page stays in that page's folder. Do not create new top-level folders such as `src/auth`.
- **UI:** Ant Design components only. No Tailwind, no SCSS. Use `ConfigProvider` tokens for theming; plain CSS or CSS modules for small custom styles. Every button, input, dropdown and date picker is 40 px high, set once in the theme (`src/theme/controlHeight.ts`, ADR-016): never set a height on one. The floating buttons are the exception (48 px, `FloatingPillButton`).
- **Charts:** draw every chart with Recharts (ADR-064), never a second charts library. Take colors from the theme (`src/theme`, such as `memberColors.ts`), and always write the numbers in text beside a chart (a list or table), so nothing depends on a tooltip, which a phone only shows on a tap. In tests wrap the file in `vi.mock('recharts', …)` with `withFixedSize`.
- **Corner radius:** only these values, from `src/theme/radius.ts`: `RADIUS.inner` (10) for small things inside others (buttons, inputs, icon tiles), `RADIUS.card` (20) for every card (a card may also take 30 px, `RADIUS.cardLarge`, for a roomy card such as the balance rows, PRD 5.21, and the member cards, PRD 5.9) and `RADIUS.outer` (24) for other containers (panels). Cards also share one padding (`CARD_PADDING`, 10) and the border of a button, set in the theme. Never hard-code another radius, and don't use `shape="round"` buttons. The only exception is the pills and round chips of the phone-first pages (group page, add expense) and the Add member and Add account buttons: `PILL_RADIUS` in `src/theme/radius.ts`, ADR-030. Every bottom sheet and dialog has the page's grey background (one rule in `src/index.css`).
- **Money:** integer minor units, always with a currency code. Respect each currency's decimal places. Multi-currency has no conversion; balances are per currency.
- **IDs:** UUID primary keys, never auto-increment.
- **Rows:** every synced row has `updated_at` and `updated_by`. Delete by setting `deleted_at` (soft delete), never hard delete synced rows.
- **Database:** create and access PGlite only through `getDb()` (single module). Never put photos or large blobs in PGlite.
- **Photos:** access only through the `PhotoStore` interface (`savePhoto`, `getPhoto`, `getThumbnail`, `deletePhoto`) from `photoService.open(accountId)` in `src/services/photoService`, backed by IndexedDB (one database per account).
- **Logs:** log through `logService.scope('<part>')` (ADR-048), never `console` directly. Lines carry ids, counts, statuses and timings only: no names, emails, descriptions, notes, amounts or tokens (the logger drops fields named like them, but do not pass them). New actions in the expense, group and person services get an entry in their `logActions` call. Every place that logs has a test of its lines (`captureLogs`).
- **Backup:** a new table or column must reach the backup and group files (`exportAll`, `exportGroup`, `backupService/schemas.ts`, the merge) or be listed in `NOT_BACKED_UP` with its reason; `backupService/__tests__/completeness.test.ts` fails until it does, and needs test data for it (ADR-044).
- **Sync:** one JSON file per member per group in the group's Drive folder; each file has a single writer. Merge by newest `updated_at` per row (user id as tie-breaker), keep edit history. Validate all downloaded JSON with zod; treat it as untrusted.
- **Storage:** one database per signed-in Google account on a device. Only one tab may open the database.
- **Offline:** the app must render and work offline. Network failures (sign-in, Drive, sync) must degrade gracefully.
- **Privacy promises:** the welcome page promises no backend, no ads and no tracking. Never add analytics, tracking or a server that stores user data without updating the welcome page and `docs/ADR.md` first.
- **Secrets:** never commit `.env*` files or tokens. The Google client ID goes in `VITE_GOOGLE_CLIENT_ID`.
- **Tests:** every functional requirement in `docs/PRD.md` must have an automated test. Split calculations, balance maths and the sync merge need unit tests; data functions (services) are tested against in-memory PGlite; pages and forms get component tests with `@testing-library/react` and `@testing-library/user-event` in jsdom (use `// @vitest-environment jsdom` at the top of the file), which type, click and read the screen the way a user does and use a real in-memory database, not mocked queries. Test files live in a `__tests__` folder beside the code they test. Make sure a new test can fail: briefly break the code it covers (flip an order, remove a check) and see the test fail, then restore it. A test that passes for the wrong reason, such as an early `null` before the checked branch is reached, proves nothing. Tests must not depend on styles: `renderPage` turns off Ant Design's runtime CSS (`zeroRuntime`) because it makes a run about a third faster, so match a button by the end of its name with `named()` and check a closed drawer by its hidden class, not by `queryByRole` (ADR-029). A test file should stay under about 15 s on its own; split a bigger one by topic with a `helpers.tsx` beside it. A feature is not done until its requirements are tested and `bun run test` passes.

## Component code style
- **Keep `return` short.** When a component's `return` grows past roughly 10–20 lines, move parts into `render<Section>()` functions (`renderHeading()`, `renderIosInstructions()`) defined inside the component, above the `return`. Prefer a plain `if` inside a render function over nested ternaries. Example: `pages/welcome/components/InstallCard/index.tsx`.
- **Render one list item with a function.** When mapping a list, write `render<Item>(item: Type)` and use `LIST.map(renderItem)`. Export the item type from the content file (`Feature`, `PrivacyPoint`, `Highlight`). Pass values the function needs as parameters (`renderAvatar(profile)`) when TypeScript would lose a narrowing check inside a nested function.
- **Inline one-off styles.** Write a small style object directly on the element (`style={{ … }}`). Don't create a `wrapperStyle` or `cardStyle` variable for something used once.
- **No dead code.** Remove props and branches that no caller uses (the old `embedded` prop on `InstallCard` was removed once only one layout remained).
- **Move data out of the component.** Copy, step lists and other data go in `content.ts(x)`; colors and similar constants go in `style.ts`.
- **Type constants explicitly and reuse shared types.** For example `WARNING_ICON_COLOR: Record<ColorScheme, string>`, where `ColorScheme` is exported from `src/hooks/useColorScheme`, so a missing key or a typo is a compile error.
- **Form fields take `id`.** A component used as an Ant Design form field takes `id`, `value` and `onChange`, and passes `id` to the control inside it (`CurrencySelect`, `MemberSelect`). The form item hands the `id` down so its label is tied to the input: clicking the label focuses the field and screen readers can name it.
- **Document non-obvious props.** Add a `/** … */` comment that says what the prop means, what changes when it is true and when it is false, and where its value comes from (`gated` and `canPrompt` on `InstallCard`).
- **Descriptive names.** Name constants for what they hold (`WARNING_ICON_COLOR`, not `WARNING_ICON`).
- **Spelling:** use "color" (not "colour") everywhere: identifiers, comments, docs and copy.

## Working agreement
- Do not implement features until the user says where to start. Work on one feature at a time.
- Ask lots of clarifying questions before implementing any code. Settle requirements, edge cases and copy first, record decisions in `docs/PRD.md` and `docs/ADR.md`, and start coding only when the user says so.
- Ask before big or irreversible changes (deleting data, changing the schema shape, swapping a library).
- **UX changes: no tests, `tsc` or lint until approved.** For a UX or visual change, implement it and check it in the browser pane, then wait: do not add, rewrite, delete or run any test, and do not run `bunx tsc -b` or `bun run lint`, until the user has seen the change and approved it (unless they ask for a run). Once they approve, fix and add the tests (with break-checks), run `bunx tsc -b`, `bun run lint` and `bun run test`, update the docs, and commit, push or deploy only as asked. Say plainly which edits are still unchecked.
- When a decision changes, update `docs/ADR.md` (and `docs/PRD.md` if behaviour changes) in the same change.
- **End each turn with clickable next steps, every time.** The user does not want to type replies like "Approved", "Start building" or "Commit, push and deploy". Before the closing message of every turn that leaves a decision or a next step (including turns that only discuss, plan or report a fix), call `wrap_up` with an `ask` and `actions` (the likely next step first, a realistic alternative second). If the notice says the user may be on Remote Control and may not see that box, also put the same choices in an `AskUserQuestion` call (its options are clickable there) instead of asking them to type. Never end such a turn with only "reply X to do Y" text. This was asked more than once; a turn that ends without buttons is a mistake. The box the user wants after every response looks like this: a short recap, one question ("What next for the experiment?") and two buttons, the likely next task first ("Finish it", whose message spells out the whole task, for example: set the animation time back, run tsc, lint and the tests, update the docs, commit on the branch) and an open alternative second ("More changes", whose message ends with a colon for the user to complete). When there are more than two sensible next steps (for example "Commit only", "Commit and finish", "Finish and deploy", "More changes"), the `wrap_up` box holds only two, so also ask with `AskUserQuestion` listing them all (up to four, the likely one first, each with a short description of exactly what it does), so the user can pick one with a click. The user approved this format ("this is perfect"): a question "What should I do next?" with options such as "Commit only" (commit what is done, nothing else), "Commit and finish" (the full remaining task, spelled out), "Finish and deploy" (the same, then merge, push and deploy) and "More changes" (keep working; the user says what), each option's description saying exactly what will happen. Use it after every response that leaves a choice.
- Only commit when asked. Before every commit read `git status` and stage files by name; never use a blind `git add -A`. Files such as `google-settings.json` (a Google OAuth download with a client secret) and `.env*` must never be staged.
- Run shell commands from the project root (give the full path with `cd`), because the working directory persists between commands.
- **Checking animations and view transitions:** the browser pane's page often reports `document.visibilityState` as `hidden`, and then no view transition runs at all. Check them in headless Chrome instead (it is always visible): `playwright-core` installed outside the repo (`bun add playwright-core` in a scratch folder), `chromium.launch({ channel: 'chrome', headless: true })` with a 402 x 874 viewport, the dev server at `/ownledger/`, a guest made through the UI ("Continue as a guest", then Create group), a style tag that sets `animation-duration: 12s !important` on `::view-transition-group(*)`, `::view-transition-old(*)`, `::view-transition-new(*)` and `::view-transition-image-pair(*)` for slow motion, and `page.screenshot()` at fixed times; read the PNGs back. The browser pane works too while its page reports `visibilityState` as `visible` (check first). For a shared-element transition between two pages (pieces that morph, a background that changes in place under sliding content), follow the technique in ADR-060.
- After a UI change, check it in the browser pane (dev server at `/ownledger/`; `?platform=ios|android|desktop` and `?installed=1` simulate the install cases), at phone and desktop widths. For a UX change, stop there until the user approves (see the rule above); for any other change, run `bunx tsc -b`, `bun run lint` and `bun run test` before saying it is done. Without the browser pane (for example in a cloud session), use headless Chromium through Playwright; signed-in pages can be reached without Google by writing a profile to `localStorage` under `ownledger-session` (`{"state":{"profile":{"id","email","name"}},"version":0}`) before opening them.
