# Architecture Decision Records

_Last updated: 2026-10-28_. Each entry: context, decision, alternatives rejected, consequences. Update an entry (or add a new one) whenever a decision changes.

## ADR-001: React + Vite, client-only (no Next.js)
- **Context:** The app stores everything locally and has no server work to do.
- **Decision:** Plain React 19 with TypeScript, built with Vite.
- **Rejected:** Next.js, because SSR and server features are unused.
- **Consequences:** Static hosting over HTTPS is enough. No backend to maintain.

## ADR-002: PGlite for the local database
- **Context:** The app needs joins, foreign keys and thousands of rows, locally in the browser.
- **Decision:** PGlite (Postgres compiled to WASM).
- **Rejected:** SQLite WASM (also viable; lighter, more mature, single-file backups), sql.js, Dexie/IndexedDB (not SQL).
- **Consequences:** Real date types and `NUMERIC`, and a path to a Postgres backend later. Larger bundle and a younger project that may have breaking changes between versions.

## ADR-003: IndexedDB storage for PGlite (`idb://`)
- **Context:** The OPFS backend is faster but fails on Safari (limit of 252 open handles). The app must work on iOS.
- **Decision:** Use `idb://`. Create the database only through `getDb()` so the backend can change later.
- **Rejected:** `opfs-ahp://` (no Safari), `memory://` (no persistence).
- **Consequences:** PGlite loads the whole database into memory, so memory grows with data size (fine for tens of thousands of rows). Only one tab may open the database. A move to OPFS later needs a worker and a dump/restore migration.

## ADR-004: Drizzle ORM
- **Decision:** Drizzle with `drizzle-orm/pglite`; `drizzle-kit` generates SQL migrations, which are bundled and run at startup in the browser.
- **Rejected:** Kysely, Prisma and classic ORMs (poor browser or PGlite fit), raw SQL (no type safety).
- **Consequences:** Typed schema and queries; browser migration runner must be written by us.

## ADR-005: Ant Design only for UI
- **Decision:** Ant Design 6 for all UI (its icons are inside its components; the app's own icons are Tabler, ADR-066). Theme via `ConfigProvider` tokens. Plain CSS or CSS modules for small custom styles (one exception: the date calendar, ADR-033).
- **Rejected:** Tailwind (style clashes with Ant Design's reset, two styling systems), SCSS (not needed).
- **Consequences:** Charts are outside Ant Design: they are drawn with Recharts (ADR-064), and the app's own icons come from Tabler (ADR-066).

## ADR-006: Receipt photos in IndexedDB via `idb`
- **Decision:** Photos live in a separate IndexedDB database (blobs, original size) with thumbnails in a separate store. PGlite holds only photo metadata. All access goes through a `PhotoStore` interface.
- **Rejected:** OPFS (no better durability, more browser caveats), storing photos in PGlite (memory use).
- **Consequences:** Photos share the site storage quota. Request persistent storage and monitor usage (not done yet). Photos are only safe once uploaded to Drive.
- **As built (ADR-031, phase 5):** `photoService.open(accountId)` in `src/services/photoService`; pictures are stored as bytes plus type rather than Blobs, for older Safari.

## ADR-007: Per-account local databases (superseded by ADR-035)
- **Decision:** The database and photo store names include the Google account id.
- **Consequences:** Two people sharing a device do not see each other's data. (Replaced: one set of data per device, owned by one account, ADR-035.)

## ADR-008: Personal backup with `pgDump` to Google Drive (superseded by ADR-044)
- **Status:** replaced before it was built: the backup is a JSON copy of every row that a restore merges in (ADR-044). Kept for history.
- **Decision:** A button runs `pgDump` (`@electric-sql/pglite-tools`) and uploads the SQL to the user's Drive. `dumpDataDir()` may be offered as a quick snapshot.
- **Consequences:** Portable, restorable into real Postgres. Backup is manual, because browser tokens expire after about an hour and there is no refresh token.

## ADR-009: Group sharing through Google Drive with the full `drive` scope
- **Context:** `drive.file` cannot see files created by other users unless picked through the Google Picker, which does not fit a one-click sync.
- **Decision:** Use the full `drive` scope, with the OAuth app in Testing mode (up to 100 named test users, "unverified app" warning). Each group has a Drive folder shared with members through the Drive permissions API.
- **Rejected:** `drive.file` + Picker (extra picking steps), a real backend such as Firebase or Supabase (not client-only).
- **Consequences:** Not publishable publicly without Google's security assessment. Fine for personal and small-circle use. The folder owner (the creator) holds the folder. The folder layout, who creates and shares it, and how members find it are in ADR-044.

## ADR-010: One JSON file per member per group
- **Decision:** Each member writes only their own file (for example `group1/user1.json`) holding the row versions they wrote, including edits to other members' expenses. Sync reads all other members' files, merges, then uploads their own.
- **Merge:** newest `updated_at` wins per row, user id as tie-breaker; edit history is kept; deletes are soft. UUID keys avoid collisions.
- **Consequences:** No upload conflicts. If two members edit the same expense between syncs, the later edit wins (the older one stays in history). It relies on reasonably accurate device clocks. Synced JSON is untrusted, so validate with zod.
- **Refined by ADR-044:** the file's format, merging by natural key for memberships and shares, expense events kept from every file, and one person per email across devices.

## ADR-011: Any group member can edit group data and expenses
- **Decision:** Any member can edit or delete any group expense and can add members.
- **Consequences:** Needs the merge rules above. Members must be able to share the Drive folder (do not disable "editors can change permissions").

## ADR-012: Multi-currency without conversion
- **Decision:** Amounts are integer minor units with a currency code. Balances are tracked per currency.
- **Consequences:** Home page can show several lines per group. A rounding helper must handle currencies with different decimal places.

## ADR-013: Sync downloads all photos
- **Decision:** Sync downloads all missing photos before finishing and is resumable. Data is merged and committed before photos start.
- **Consequences:** A large first sync can be slow and heavy on storage and mobile data; it stops cleanly on quota errors. (A warning before the download was planned; the user decided against it, ADR-044.) The private backup holds every photo too (ADR-044), so a restore can bring back photos of groups that cannot be shared.

## ADR-014: Installable PWA, install gate firm on iOS
- **Decision:** `vite-plugin-pwa` for the manifest and service worker. The welcome page shows install instructions. On iPhone/iPad the login button appears only in the installed app (with a "continue in browser" link); on Android and desktop, installing is optional.
- **Reason:** An installed iOS PWA has its own storage, separate from Safari, so data entered in a tab would not carry over.
- **Consequences:** Google sign-in in a standalone iOS PWA needs early testing on a real iPhone; fallback is a redirect-based flow. Keep the signed-in profile locally so the app opens offline.

## ADR-022: PWA tooling and update behaviour
- **Decision:** `vite-plugin-pwa` (Workbox `generateSW`) precaches the built files and falls back to `index.html`. `registerType: 'prompt'`: a new version is announced with a notification and applied only when the user taps Reload. Icons (64, 192, 512, maskable, Apple touch, favicon) are generated at build time by `@vite-pwa/assets-generator` from `public/logo.svg`, with no extra padding because the source already respects the maskable safe zone.
- **Rejected:** `autoUpdate` (could replace the app while the user is mid-entry); hand-made icon PNGs.
- **Offline check, and a trap found there:** a real offline run (build, `bun run preview`, let the service worker install in Chrome, stop the server, reload) showed the app did not open offline at all: the worker's install failed with `add-to-cache-list-conflicting-entries`, because `manifest.webmanifest` was in the precache twice with different revisions (once from our `globPatterns`, once added by the plugin itself), so the precache stayed empty although the worker looked active. `globPatterns` no longer lists `webmanifest`, and `scripts/deploy-pages.sh` refuses to deploy when `dist/sw.js` lists any file twice. Anyone who installed the app before the fix gets the working worker when they next open it online (the update prompt, then Reload).
- **Consequences:** The service worker exists only in production builds, so test offline behaviour with `bun run build && bun run preview`. The precache size limit must be raised when the PGlite WASM files are added. Offline caching was not confirmed in the embedded preview browser and should be checked in real Chrome (DevTools, Application, Offline).

## ADR-023: Install detection and iOS gate
- **Decision:** `src/pwa/platform.ts` detects the platform from the user agent (iPadOS reports as a touch-screen Mac) and standalone mode from `display-mode: standalone` or `navigator.standalone`. `src/hooks/useInstall` captures `beforeinstallprompt` at module load, because it can fire before React mounts. Sign-in is gated only on iOS when not installed and not skipped; `VITE_REQUIRE_INSTALL=false` disables the gate. In development, `?platform=` and `?installed=1` simulate each case.
- **Placement:** the install card is rendered inside the hero, above the sign-in button, so installing is the first thing a visitor acts on (it was originally a separate section below the hero). While gated, the card is the call to action and the sign-in button is not rendered.
- **Consequences:** The skip choice is not persisted, so iOS users see the gate on every browser visit. User-agent detection can be wrong for unusual browsers; `detectPlatform` has unit tests. Native install prompts exist only in Chromium browsers; others get written instructions.

## ADR-016: Name, look and visuals
- **Decision:** The app is called **OwnLedger**. Friendly, colorful look with a teal/green accent, applied through Ant Design `ConfigProvider` tokens; follows the system light/dark setting. Visuals come from icons (Ant Design's at first, Tabler since ADR-066), gradients and emoji.
- **Corner radius:** three values, defined in `src/theme/radius.ts`: **inner 10 px** for small things inside other things (buttons, inputs, icon tiles; 12 px at first, 10 px since ADR-061), **card 20 px** for every Ant Design card (set on the theme's `Card` component, ADR-061) and **outer 24 px** for the other containers (panels, collapse, the hero logo tile). They are applied as Ant Design tokens (`borderRadius`, `borderRadiusSM`, `borderRadiusXS` = inner; `borderRadiusLG` = outer). Large buttons and inputs would otherwise inherit the outer radius and look like pills, so `Button`, `Input`, `InputNumber`, `Select` and `DatePicker` override `borderRadiusLG` back to inner. Buttons use the default shape, not `shape="round"`. Circles (avatars) are exempt.
- **Control height:** every button (any size or type, including icon-only and the small inline pills), text input, dropdown and date picker is 40 px high. It is set once, in the theme: `controlHeight`, `controlHeightSM` and `controlHeightLG` are all `CONTROL_HEIGHT` (`src/theme/controlHeight.ts`), so Ant Design's small, middle and large sizes come out the same and a page never sets a height. Primary buttons have the same size and text as the others. Exceptions: the floating buttons are 48 px with 16 px text and 24 px padding (`FloatingPillButton`, ADR-030); the remove badge on a receipt photo stays 24 px, since 40 px would cover most of the photo; the receipt tile (the camera button) stays 64 px to match the photos beside it; the big amount field of the add-expense form is 40 px with 20 px text instead of 32 px; the multi-line Notes box keeps its own height; the add-expense currency button is a 40 × 40 px square showing the symbol (`currencyService.symbol`: the locale's regular symbol so dollars stay distinguishable, else the short symbol when no other currency shares it, else the code), with the font size chosen by length (`labelFontSize`). A consequence in the tests: a dropdown's options are 40 px tall, so Ant Design's virtual list renders fewer of them (about seven), and a test must pick an option near the top of the list.
- **Rejected:** Custom SVG illustrations or supplied image assets (more work, no need yet), Ant Design's default blue.
- **Consequences:** No image assets to maintain. Visual polish is limited to what icons, color and layout can do. The name's trademark and domain availability were not checked.

## ADR-017: Open source under GPL-3.0, public repository
- **Decision:** The code is public at https://github.com/omkarsheral1989/expense-tracker under GPL-3.0 (`license` field is `GPL-3.0-only`). The welcome page says so and links to the repository.
- **Consequences:** Derivative works must also be GPL. The privacy claims on the welcome page are verifiable by reading the code, which also means they must stay true (see ADR-018).

## ADR-018: Welcome page privacy claims are commitments
- **Decision:** The welcome page states: offline first, no OwnLedger servers, no ads and no tracking, user owns the data. These constrain the codebase: no backend storing user data, and no analytics, tracking or ad SDKs. The FAQ states honestly that the Google Drive permission is broad (full `drive` scope) and that the app only uses its own folders.
- **Consequences:** Adding analytics or a backend later requires updating the welcome page and this ADR first. Avoid unqualified claims such as "very secure".

## ADR-019: Google sign-in button and token flow
- **Decision:** A custom Ant Design button with the Google "G" logo, following Google's branding rules for wording and logo, started by `useGoogleLogin` (implicit flow) from `@react-oauth/google`. Sign-in asks for **basic scopes only** (`openid email profile`); the Drive scope is requested later, at the first backup or sync (incremental consent, a second prompt). The profile is read from Google's userinfo endpoint and validated with zod.
- **Without a client ID:** `useGoogleLogin` throws while rendering when the client ID is empty, which would blank the page. The provider and Google's script are skipped, and a separate button only explains that sign-in is not configured.
- **Rejected:** Google's official rendered button (`GoogleLogin`), which returns an ID token and fits poorly with the token flow needed for Drive access.
- **Consequences:** The button must be triggered directly by a user click (popup blockers). Tokens last about an hour with no refresh token, so Drive actions may re-prompt. Because the OAuth app stays in Testing mode (ADR-009), users see Google's "hasn't verified this app" screen, and only people added as test users can sign in ("Access blocked" otherwise). The FAQ explains both and points people who are blocked to the GitHub issues page (https://github.com/omkarsheral1989/expense-tracker/issues) to request access.

## ADR-024: Session handling
- **Decision:** The signed-in profile (Google id, email, name, picture) is persisted in `localStorage` (zustand `persist`, key `ownledger-session`) so the app opens offline without a new Google login. The access token is kept in memory only and is requested again when a Drive action needs it (`validToken` treats a token with under a minute left as expired). Signed-in visitors to `/` are redirected to `/home`; signed-out visitors to `/home` go back to `/` (`RequireAuth`).
- **Across tabs:** every open tab follows the stored session. The browser's `storage` event tells the other tabs when one changes it, and the `useSyncSessionAcrossTabs` hook (`src/hooks/useSyncSessionAcrossTabs`, called once in `App`) reloads the profile from storage, or signs the tab out if the session was removed or cleared. So signing out in one tab signs out all of them, and signing in shows up in the others. The in-memory access token is never shared; a tab without one asks for its own when a Drive action needs it. The database tab lock (ADR-026) still lets only one tab open the data.
- **Sign-out:** clears the session and token only. The account's local database and photos stay on the device, and signing back in restores them. Google's access is not revoked.
- **Consequences:** "Signed in" means "this device remembers who you are"; it is not proof of a current Google session. Anyone with access to the browser profile can open the app, so a future app lock may be wanted (see PRD open questions).

## ADR-020: Placeholder home route (superseded by ADR-028)
- **Status:** replaced by the real home page (ADR-028). Kept for history.
- **Decision:** Until the home page was built, a successful sign-in routes to `/home`, a simple "Signed in as <name>" page with a sign-out button.
- **Consequences:** Temporary; replaced when the real home page was implemented.

## ADR-025: Data model for people and groups
- **Decision:** three tables. `people` holds one row per person, identified by lower-cased email (unique; optional since ADR-034), with an optional name; the signed-in user is a person too. `groups` has a name (1 to 60 characters), a type (`trip`, `home`, `couple`, `other`, enforced by a check constraint), a required `default_currency` (a three-letter upper-case ISO 4217 code, checked by a constraint; added in the second migration) and `created_by`. `group_members` links a person to a group (unique per pair). Every table has a UUID primary key, `updated_at`, `updated_by` (a person) and `deleted_at`, as the sync design requires. "Pick an existing member" reads from `people`.
- **Default currency:** the group's currency only pre-fills new expenses. It does not stop an expense from using another currency, and nothing is converted (ADR-012). The picker offers all ISO currencies (from the browser's `Intl` data) and preselects the one for the device's region.
- **Rejected:** keeping members as an email list inside each group (no shared list of known people, and no clean per-member rows for splits and balances later).
- **Consequences:** `updated_at` is set by the application on every change; there is no database trigger. Group members must be `@gmail.com` addresses (a product rule, checked in the app, not the database), so Google Workspace users with other domains are excluded for now.

## ADR-034: Adding a member through a dialog; people without an email
- **Context:** the members field accepted any typed `@gmail.com` address as a new person. The product now adds a new member through an explicit "Add a new member" dialog with a name and an optional email.
- **Decision:**
  - **Schema (migration 0004):** `people.email` becomes nullable. It stays unique and lower-case when present (Postgres treats NULLs as distinct, so any number of people may have none). Everything that reads `people.email` handles null; a person is identified by `id`, not by email.
  - **Saved at once:** the dialog calls `personService.addPerson(db, user, { name, email })`, which validates with zod, saves the person on this device and returns field errors rather than throwing (ADR-027). The create-group form then holds selected people by id.
  - **Rules:** name 1 to 60 characters and unique on this device (ignoring case and extra spaces, counting the user and people with no email); email optional, `@gmail.com` when given, unique. Both uniqueness checks run in the save function and come back as field errors naming the existing person. They are a convenience on this device (ADR-027); the same person may exist under different names on other devices.
  - **Group service:** `groupService.createGroup` takes `memberIds` (ids of people already saved) in place of `memberEmails`; the page and test helpers that build groups by email change with it.
  - **Members field:** typing only filters; "Add a new member" is the last row of the list. A person with no email shows "No email" where the email would be (field, members sheet).
  - **Sync:** a member without an email cannot be shared the group's Drive folder (ADR-009, ADR-010), so they stay on this device until an email can be added (open question in the PRD).
- **Rejected:** a placeholder email for people without one (messy for sync and duplicates), keeping both `memberEmails` and `memberIds` (an input the app no longer uses), and blocking only same-named people who have no email (a name is the only thing that tells them apart in the lists).
- **As built:** `src/services/personService` (`addPerson`, schemas, `findOrAddPerson` moved out of `groupService`; the `@gmail.com` rule and `memberEmailDomain` moved with it). `groupService.listKnownPeople` now lists everyone saved on the device except the user (it used to list only people from the user's groups), so a person added in the dialog is listed at once; `groupService.displayName` and `shortName` take an optional email. The members field is an Ant Design `Select` in `multiple` mode with "Add a new member" appended to its list through `popupRender`; its list is closed (`open` held in state) when the dialog opens over it. The dialog is `AddMemberDialog`, built on `AdaptiveDialog`.
- **Tests:** `src/testing/groups.ts` has `createTestGroup` (a group with members given by email, adding any who are not saved yet), `addTestPerson` (a person with a name and optionally an email, as the dialog would save them) and `memberIdsOf`. The existing tests keep creating groups by email through `createTestGroup`. The dialog's fields get a form `name` of their own (`addMember`), because two forms on the page with a field called "name" gave both inputs the same `id` and the dialog's label pointed at the group name input.
- **Consequences:** schema shape changes (asked and approved); migration 0004 only drops `NOT NULL`, so existing databases keep their data. People saved before this change have an email and no name, so a new person's name never clashes with them.

## ADR-035: Guest mode and one set of data per device
- **Context:** the app required Google sign-in before anything else, and every database, photo store and service call was keyed by the Google account (its id for storage, its email for "who is the user").
- **Decision:**
  - **Guest mode:** the welcome page's button is "Open OwnLedger" and opens `/get-started` (the route and the page folder keep their first name) (Sign in with Google, "OR", Continue as a guest, with a note that sign-in is needed for backup and sharing). A guest has no email: their person row is named "Guest" with `email` null (ADR-034 made that possible).
  - **One dataset per device**, with no separate guest and signed-in data. A small device record in `localStorage` (`ownledger-device`) holds the dataset id (it names the PGlite database and the photo store, as the account id did), the id of the user's person, and the owner (a Google account id and email, or none for a guest). It is written before the data is opened and read by `useDatabaseSession`.
  - **Signing in** with Google while the dataset has no owner makes that account the owner: the user's person gets the account's email and name. If a different person in the data already has that email, the guest person is merged into that person (every reference to the guest's id is re-pointed in one transaction, then the guest row is removed), so there is one person per email. Nothing is asked and nothing is copied.
  - **One Google account per device:** a different account signing in on a dataset owned by another is refused with a message naming the owner. Signing out keeps the data; "Continue as a guest" opens the same dataset.
  - **Existing users:** with no device record, a Google sign-in uses the database already named for that account (`ownledger-<account id>`, which is what ADR-007 created) as the dataset, so nobody loses data. A device that already holds databases for several accounts keeps them, but only the first account to sign in after this change owns the device record.
  - **Services identify the user by person id,** not email: `listGroups`, `getGroup`, `expenseService.*` and the rest take `userId` (the person's id) in place of `userEmail`; `createGroup` takes the creator's person id. The session store holds either a Google profile or a guest marker.
  - **Install gate:** "Open OwnLedger" is gated on iPhone/iPad exactly as Sign in with Google was (ADR-014, ADR-023), for the same reason: an installed iOS app has storage separate from Safari.
- **As built:** `deviceService` (the `ownledger-device` record; `forGuest`, `forGoogle`, `setUserPersonId`), `userService.resolve` (finds, adds, links or merges the user's person when the data opens; `mergePeople` re-points every reference in one transaction and adds together the two shares of an expense both were in), `useCurrentUser` (context provided by `DatabaseGate` once the data is open and the person found; pages call the services as `user.personId`), `useInstallGate` (the iOS gate, shared by the welcome page and that page; "Continue in browser anyway" now lasts until the page is reloaded, across pages, and development overrides such as `?platform=ios` are read once at load so they also survive moving between pages), and the page behind the button (`/get-started`). The auth store holds `profile` or `guest`; `signOut` leaves either. `DatabaseGate` shows a refusal screen when the data belongs to another account, and `useSignIn` shows the same message in a dialog before anything is stored.
- **Tests:** a page is rendered with the current user the way `DatabaseGate` provides it: `renderPage` reads the auth store (a profile, or the guest flag) and gives the page a person id worked out from the email (`personIdForEmail` in `src/testing/ids.ts`, a deterministic valid UUID). The test helpers (`createTestGroup`, `addTestPerson`, `ensurePersonId`) save people under the same ids, so the signed-in user of a page test and the person the helpers create for that email are the same person without a lookup. A test that renders a page saves the user's own person itself (the gate does it in the app). Tests that touch Google sign-in mock `config.ts` (`GOOGLE_CLIENT_ID`) so they do not depend on a developer's `.env.local`.
- **Rejected:** a separate guest database that is copied into the account on sign-in (two places for data, duplicate people, and the user did not want a choice); asking the user whether to keep guest data; a made-up email for the guest (it would leak into screens and sync).
- **Consequences:** the biggest change to the services and tests since the data model: every call that took an email changes, and the test helpers (`createTestGroup`, `addTestExpense`, `expenseInput`, `personIdOf`) change with it. The device record in `localStorage` is a single point of failure: if it is cleared while IndexedDB is not, a guest's data cannot be found (a signed-in user's can, by the account's database name). Group sharing and sync (ADR-009, ADR-010) need a person with an email, so they are unavailable to a guest.

## ADR-036: Editing a group
- **Context:** the group page's gear button was switched off (ADR-030) and groups could not be changed after creation.
- **Decision:** the gear became an Edit (pencil) button that opens its own page, `/groups/<id>/edit` (`src/pages/editGroup`), like Create group rather than a dialog. It edits only the group's name, type and default currency; members are left for later. Any member can save (ADR-011).
  - **Service:** `groupService.updateGroup(db, userId, groupId, { name, type, defaultCurrency })` validates with `updateGroupSchema` (the create schema's three fields, so the rules exist once, ADR-027), checks membership and the name in one transaction, sets `updated_at` and `updated_by`, and returns field errors, or `{ ok: false, notFound: true }` for a group the user cannot see (unknown, deleted, or not a member, which look the same as on the group page). The same-name check is `createGroup`'s, except the group being edited is excluded, so its own name (or its case) is allowed.
  - **Activity:** changing the group sets its `updated_at`, which moves it to the top of the home list (ADR-028).
  - **Form:** the page reads the group with `getGroup` (so a non-member sees "Group not found") and the form, `EditGroupForm`, holds the opening values to tell if anything changed: unchanged means Save only goes back, with no write, and Back asks "Discard your changes?" only after a change.
  - **Shared pickers:** `CurrencySelect` and `GroupTypeSelector` moved from the create-group form to `src/components`, since two pages use them.
- **Rejected:** a dialog or drawer (the form is the same size as Create group's and has its own address), saving each field on its own (a different pattern from Create group), and a settings page that also holds members, leave and delete (their rules are still open questions in the PRD).
- **Consequences:** a name check is still only a convenience on this device (ADR-027): another member may rename to a name that exists in another member's list, and sync will have to merge the two. Concurrent edits to a group's details follow the usual newest-`updated_at` rule (ADR-010).

## ADR-037: Settle up (payments between members)
- **Context:** balances are derived from expenses (ADR-031), and the "Settle up" pill on the group page was switched off (ADR-030). Members pay each other outside the app and need to record it.
- **Decision:** a payment is saved as an ordinary expense in the `settlement` category, with the description "Payment" and the `exact` method: the payer paid all of it (`paid_minor` = the amount), the recipient owes all of it (`owed_minor` = the amount), and every other member has 0 and 0. Nothing in the balance maths changes: the payer's net rises by the amount and the recipient's falls by it, which cancels what the recipient was owed.
  - **Service:** `expenseService.createSettlement(db, userId, groupId, { payerId, recipientId, amountMinor, currency, date, notes, receipts })` builds that expense and calls `createExpense`, so the rules (amount, currency, date, notes, photos, members only) exist once and everything is saved in one transaction. It returns field errors, named for the settle-up form (`payerId`, `recipientId`, `amountMinor`, …). The recipient rules are its own: empty gives "Choose who received it.", the payer gives "Choose someone other than the payer.", a non-member gives "Choose someone from the group."; with no usable recipient the split is left empty, which cannot add up, so nothing is saved (a payer who is also the recipient would add up, which is why it is checked explicitly). Any member may record a payment for any two members.
  - **Category:** `settlement` is a one-category group of its own, after Utilities. `expenseService.categoryGroups`, which the category picker lists, leaves it out, so an expense cannot be given it by hand in the app; `categories`, `categoryOf` and `isCategoryKey` know it (so the list and the details page can show it, and synced rows validate).
  - **Wording:** `expenseService.settlementSentence(payer, recipient)` ("You paid Priya", "Priya paid you", "Priya paid Sam") and `titleOf(expense)` (the sentence for a settlement, the description otherwise) are shared by the list row, the details page and the tab title. The list item carries `recipient` only for a settlement (the share that owes it all).
  - **List row:** a payment is one line with no tile and no status (see the PRD), because the sentence and the amount say it all and a lent or borrowed amount reads strangely for money that changed hands. The date column of every row is 48 px high.
  - **Page:** `src/pages/settleUp` (`SettleUpForm`). It reuses the add-expense fields, which moved from the add-expense page to `src/components` (`AmountInput`, `CurrencyField`, `DateField`, `ReceiptsField`) since two pages use them. The payer and recipient are plain Ant Design `Select`s; the recipient list leaves out the payer.
- **Rejected:** a separate `settlements` table (a schema change, and balances, edit, delete and sync would each need a second code path), a split dialog for payments (two people and one amount need none), a "payment" flag next to the category (a second way to say the same thing), and a made-up description per payment (the sentence is worked out from the shares, so it follows renamed people).
- **Consequences:** a payment shows in the expense list and counts as an expense for the group's activity (ADR-028). It is created and read like any expense, so editing, deleting and sync (ADR-010) will treat it like one. The description "Payment" is only stored text: screens never show it. Debts between three or more people are not simplified (ADR-031); a payment settles one pair.
- **Not decided yet:** suggesting the person and amount from the balance, and editing or deleting a payment.

## ADR-038: Adding members to an existing group
- **Context:** members could only be chosen when a group was created (ADR-025, ADR-034). Any member may add members (ADR-011).
- **Decision:** the members sheet on the group page (ADR-030) ends with an "Add member" button that opens an "Add a member" sheet (`AdaptiveDialog`: a bottom sheet on phones, a centered dialog on wide screens). It lists the people saved on this device who are not in the group, with search, ticks and Cancel / Add buttons; "Add a new member" opens the same name-and-email dialog as Create group, saves the person at once (ADR-034) and ticks them in the list, but does not add them to the group: only Add does, together with anyone else ticked.
  - **Service:** `groupService.addMember(db, userId, groupId, personId)`, one person at a time, in one transaction. It checks that the group is live and the user is a live member, and that the person exists; an unknown person or one already in the group comes back as `{ ok: false, message }` (naming them), a group the user cannot see as `{ ok: false, notFound: true }` (the same for unknown, deleted and not-a-member, as elsewhere). A person who left (their membership has `deleted_at`) is added back by clearing it, because `group_members` is unique per group and person; otherwise a membership row is inserted. It sets `updated_at` and `updated_by` on the membership and on the group, which moves the group to the top of the home list (ADR-028). The page adds the ticked people one after another and stops at the first problem; those already added stay added and the group is read again.
  - **Shared pieces:** `MemberSelect` (with `AddMemberDialog`) moved from the create-group form to `src/components`, since the new-person dialog is used in both places. The sheet's own list is `PickMemberDialog` in `MembersSheet/AddMemberRow`; it is given a new `key` on each opening, so it starts with nobody ticked.
  - **Reading the group again:** the group page's `useAsyncData` now has `keepPrevious` (ADR-031), so after a member is added the page and the members sheet stay on screen while the group is read again, instead of showing the loading placeholder and losing the sheet. The cost: if a group page is shown for a different group id without leaving the page, the earlier group's data stays until the new group has loaded (not possible from the app's own links, which go through the home page).
  - **Stacked sheets:** a sheet opened from inside another pushes the first up by 180 px (Ant Design's default `push`); the app leaves it on for every drawer. The new-person dialog is rendered inside `PickMemberDialog` in the component tree (it is drawn on the page, not inside the sheet), so it pushes that sheet in turn.
- **Rejected:** an inline people field inside the members sheet (it needed its own width and a dropdown inside a sheet), adding a new person to the group at once (the user wanted to see them in the list first and confirm with Add), and ticking only one person (Add and Cancel suggest a choice that can hold several).
- **Consequences:** a person saved through "Add a new member" stays saved on the device even if Add is never pressed. Adding people who have no email is allowed, with the same limit as in Create group: they cannot be shared the group's Drive folder (ADR-009, ADR-010) until an email can be added.
- **Tests:** `src/pages/group/__tests__/addMember.test.tsx` finds a stacked sheet by its title text (`findSheet`): in jsdom Ant Design gives every sheet the same `aria-labelledby` id, so the accessible name of a sheet over another is the first one's and a role-and-name query finds the wrong sheet.

## ADR-039: Editing an expense, with a stored history
- **Context:** the details page's Edit button was switched off (ADR-030). Any member may edit any expense and the history must be kept (ADR-010, ADR-011); the page that shows the history comes later.
- **Decision:** (the history table below is replaced by `expense_events`, ADR-042; the service, form and page parts still hold)
  - **History table (migration 0005):** `expense_revisions` has the usual sync columns (ADR-025) plus `expense_id`, `edited_by` (a person), `edited_at` (a timestamp), `before` (`jsonb`: the whole expense as it was before the edit: description, category, amount, currency, date, notes, method, one entry per share with paid, owed and input value, and the photo list with id, position, type and size) and `changes` (`jsonb`: one entry per changed field with its old and new value; fields: `description`, `category`, `amount`, `currency`, `date`, `notes`, `paidBy`, `split`, `receipts`, where `receipts` holds the photo ids before and after, in order, so what was added and removed can be told). A revision is only ever inserted: never updated or deleted, so `updated_at` equals `edited_at` and `deleted_at` stays null. The current version stays in `expenses`, `expense_shares` and `expense_photos`; the newest revision is the version before the last edit, so the history of an expense is its revisions oldest to newest followed by the current row. Large `before` snapshots hold no photo bytes, only ids (ADR-006).
  - **Service:** `expenseService.updateExpense(db, userId, groupId, expenseId, input)` validates with the create schema (one set of rules, ADR-027), checks in one transaction that the user is a live member and that the expense is live and in that group, recomputes the shares with `computeShares` over the group's members, works out what changed, and when something did: inserts the revision (the shares are only worked out again when the amount, the payer or the split changed, so editing the notes never moves anyone's part, even when a member joined since), updates the expense (`updated_at`, `updated_by`), rewrites its shares in place (a person with no part gets 0 and 0, keeping the row), soft-deletes removed photo rows and inserts new ones, and renumbers positions. Nothing changed means no write and a result that says so. It returns field errors, `{ ok: false, notFound: true }` for an expense the user cannot see (as `getExpense`) and the same for a payment, which cannot be edited. It reads the expense in the same transaction, so a concurrent edit in another tab is compared against what was actually stored.
  - **Time:** `edited_at` is the device's clock when the edit is saved, like every `updated_at` (ADR-010 already relies on reasonably accurate clocks).
  - **Photos:** a photo removed in an edit is soft-deleted in `expense_photos` and its picture stays in the photo store, so an earlier version can still show it; a cleanup rule is the same open question as for deleted expenses (PRD). Pictures added during a failed save are removed again, as in `createExpense`.
  - **Form:** the add-expense form moves to `src/components/ExpenseForm` (with its category and split fields) and both pages use it: add expense passes empty values and the group switcher, edit expense (`src/pages/editExpense`) passes the expense's values and no switcher. It follows the edit-group page for "nothing changed" and "Discard your changes?" (ADR-036).
  - **Details page:** `getExpense` also returns the newest revision's editor and time (`lastEdit`), shown as a grey "Edited by …, date, time" line under who paid. (Not shown any more: ADR-056.)
- **As built:** `expenseService.getExpenseToEdit` (the form's own terms: payer, method, what was entered per person, photos), `updateExpense` and the pure `expenseChanges` / `sameSplitInput` in `utils.ts`; `getExpense` returns `lastEdit` (the newest revision's editor and time). The form is `src/components/ExpenseForm` (`ExpenseForm`, with `SaveOutcome` for what the page's save returns: saved, invalid or gone), given the opening values, a `renderGroupPicker` (the add page passes `GroupSwitcher`, the edit page the shared `GroupLabel`), the discard text, where to go back to and the save function; `FormValues` has `keptReceipts` (photos the expense already has, shown by `ReceiptsField` through `StoredReceiptPreview` and counted towards the limit of 10). `src/pages/addExpense` keeps only its thin wrapper (defaults, carry-over, switcher) and `src/pages/editExpense` the page and `EditExpenseForm`; `ExpenseNotFound` moved to `src/components` since both the details and edit pages use it. The time on the details page comes from `dateService.formatDateTime` (the day as elsewhere, the time in the device's language and clock style).
- **Rejected:** field-change rows only (an old version, especially the split, would need replaying), a snapshot with no list of changes (every history view would have to diff), overwriting with only `updated_by` (loses every earlier value), and letting an edit move an expense to another group (the split, currency default and members all depend on the group).
- **Consequences:** a schema change (asked and approved). Every edit adds a row of a few kilobytes; a rule for pruning is not needed yet. Sync (ADR-010) will carry revisions like any row. Payments are not editable until their own form exists. Restoring an earlier version would be a new edit whose changes are the reverse.

## ADR-040: The edit history on the details page; when an expense was created
- **Context:** every edit stores a revision (ADR-039). The details page should show them, with who and when, and the start of the story: who added the expense and when. An expense stores only who created it (`created_by`) and when it last changed (`updated_at`), so its creation time is unknown.
- **Decision:**
  - **Schema (migration 0006):** `expenses.created_at` (`timestamptz`, not null, default now). New expenses set it to the time of saving (`createExpense`). Existing rows are filled in by the migration: an expense never edited gets its `updated_at`, which is its creation time; one that was edited gets the time of its first revision, the earliest moment known, so such an "added" entry may read slightly late (only expenses edited between migration 0005 and this one are affected). It is a synced column like the others; it is never changed after creation.
  - **Reading:** `getExpense` returns `createdAt` and `history`: the revisions, newest first, each with the editor (as `createdBy`: email, name, `isYou`), the time, the `changes` and `currencyBefore` (the currency the expense had before that edit, to write its old cost). It also returns `people`, the names of everyone a change refers to (the payer and the people in a split, before and after, by person id), so no screen has to look anyone up. A payment has no history (it cannot be edited).
  - **Sentences:** worked out by pure functions beside the page (`historyLines`, one entry in, the lines out; nested lines for a split, in `ExpenseDetails/History/utils.ts` at first and, since ADR-043, in `src/components/ExpenseWording/history.ts`), unit-tested, so wording changes in one place. The section is `History` with one `HistoryEntry` per revision and the "added this expense" entry last. A split's person lines show what was entered, in the method's units, never the amounts people owe (which would need the version after each edit rebuilt from the next revision, and would also show effects of a new amount).
- **As built:** migration 0006 (`0006_expense_created_at.sql`, the generated `ADD COLUMN` plus two hand-written `UPDATE`s for the existing rows, tested against a database as it was before: `src/db/__tests__/schema.test.ts`); `ExpenseDetails/History` (`index.tsx`, `HistoryEntry`, `utils.ts` with `historyLines`, `historyHeader` and `QUOTE_MAX_LENGTH`, 80); the plain day "5 Oct 2026" comes from `dateService.formatDate`. The details page's tests for it are `src/pages/expense/__tests__/history.test.tsx` (edits made through `updateExpense` at faked times), and the wording is unit-tested in `History/__tests__/utils.test.ts`.
- **Rejected:** a separate history page now (the user wants it at the bottom of the details page), showing only the date of creation (the expense's own date may differ from when it was entered), leaving the "added" entry out, and showing what each person owes in a split change (see above).
- **Consequences:** a schema change (asked and approved). The history grows with every edit and is shown in full (a "show all" fold can come later if it gets long). Restoring a version later can reuse `before`.

## ADR-041: Deleting an expense (a soft delete)
- **Context:** the details page's Delete button was switched off (ADR-030). Any member may delete any expense (ADR-011), and synced rows are never hard-deleted (CLAUDE.md, ADR-025).
- **Decision:**
  - **What is stored:** `expenseService.deleteExpense(db, userId, groupId, expenseId)` sets `deleted_at`, `updated_at` and `updated_by` on the `expenses` row, in one transaction that first checks the user is a live member of the group and the expense is live and in that group. It returns `{ ok: true }` or `{ ok: false, notFound: true }` (the same for unknown, malformed, already deleted, another group's and not-a-member, as everywhere). Shares, photos (rows and pictures) and revisions are left as they are: every read already leaves out a deleted expense (the list, balances, recent currencies, `getExpense`, `getExpenseToEdit`, `updateExpense`), so nothing else changes, and the expense can be brought back later by clearing `deleted_at`. Who deleted it and when are `updated_by` and `updated_at` of the row; a `deleted` event is written too (ADR-042), so the history and the Activity page know who deleted it and when, even after a restoration.
  - **Activity:** the group's activity already takes the newest `updated_at` of its expenses, deleted ones included (ADR-028), so a deletion moves the group to the top of the home list.
  - **Payments:** a payment between members is an ordinary expense in the `settlement` category (ADR-037), so the same function deletes it; only its editing is missing. The dialog and messages say "payment".
  - **Page:** the button opens an Ant Design confirmation (`modal.confirm`, as for "Discard your changes?"): title "Delete this expense?" / "Delete this payment?", the text "It will be removed from the group, and the balances will change.", Cancel and a red Delete. The Delete button is busy and the dialog stays open while it works (`onOk` returns the promise). Success: a message and `navigate` to the group page; "not found": "This expense is no longer available." and the group page; an unexpected failure: "Couldn't delete the expense. Please try again.", the dialog closes and the page stays.
  - **Photos:** the pictures stay in the photo store, like the pictures of a photo removed in an edit (ADR-039), so a restored expense still shows them. The cleanup rule stays an open question (PRD).
- **A deleted expense stays visible (decided after the first version):** the group's list keeps it as a one-line "You deleted 'Dinner' (£9.00)" entry, like a payment's line, and its details open read-only. So `listExpenses` no longer leaves deleted expenses out: each item has `deleted: { by, at }` (the deleter is the row's `updated_by`, the time its `deleted_at`; a deleted expense is never edited, so neither changes again) and the balances, the recent currencies and every write still leave it out. `getExpense` also returns a deleted expense, with the same `deleted` field; `getExpenseToEdit`, `updateExpense` and `deleteExpense` still treat it as not found. The list's order within a day changes from the latest change to the time of adding (`created_at`, ADR-040), as the PRD always said: otherwise deleting would move the line to the top of its day, and an edit would move an expense up. The details page of a deleted expense has no Edit or Delete, a "Deleted by …" line, and its History is always shown with a first entry "You deleted this expense" (the history is otherwise only shown once edited).
- **As built:** `expenseService.deleteExpense` (a transaction: membership check, then one `UPDATE … RETURNING` of the live expense in that group, so a second deletion or another group's id finds nothing); `listExpenses` joins the deleter (`alias(people, 'deleter')`) and orders by `date`, `created_at`, `id`; `getExpense` returns `deleted`; `ExpenseRow` draws the line (`renderLine`, shared with the payment line) and `ExpenseDetails` the confirmation (`modal.confirm` from `App.useApp()`, whose `onOk` returns the promise, so Ant Design keeps the Delete button busy and the dialog open until it settles), the read-only view and, through `History`, the deletion entry (`historyHeader(by, 'deleted', noun)`). Tests: `deleteExpense.test.ts` (service), `src/pages/expense/__tests__/delete.test.tsx` (confirmation, deleting, failure, already deleted, the read-only view) and the deleted-line tests in the group page's `index.test.tsx`.
- **Rejected:** deleting at once with an Undo message (easy to miss on a phone), a confirmation and an Undo message (more to build before anyone has asked for restoring), a hard delete (forbidden for synced rows), writing a revision for the deletion, and deleting the pictures with the expense (a restored expense would show "Not on this device").
- **Consequences:** deleted expenses stay in the database and in the photo store until a cleanup rule exists. Sync (ADR-010) carries `deleted_at` like any soft delete, and the newest `updated_at` wins, so an edit made on another device after a deletion would bring the expense back; that case is not handled yet. Restoring needs a way to list deleted expenses, which does not exist.

## ADR-042: Expense events replace revisions; restoring a deleted expense
- **Context:** the edit history is stored as revisions (ADR-039) and a deletion only as `deleted_at` (ADR-041). Restoring an expense (next) needs deleting and restoring remembered for as many times as they happen, and the app is to get an Activity (or Notifications) page listing everything that happens, so every event of an expense must be recorded somewhere complete, in one place, readable without joins.
- **Decision:**
  - **One event table (migration 0007):** `expense_events` has the usual sync columns (ADR-025) plus `group_id`, `expense_id`, `kind` (`added`, `edited`, `deleted` or `restored`, a check constraint), `acted_by` (a person), `occurred_at`, `snapshot` (`jsonb`, an `ExpenseSnapshot`: the whole expense as it is right after the event: description, category, amount, currency, date, notes, method, every share with paid, owed and entered value, and the photo list with id, position, type and size; no picture bytes, ADR-006) and `changes` (`jsonb`, the list of what an `edited` event changed with old and new values as in ADR-039, empty for the other kinds). An event is only ever inserted, never updated or deleted, so `updated_at` equals `occurred_at` and `deleted_at` stays null. Indexes: `(expense_id, occurred_at)` for an expense's history and `(group_id, occurred_at)` for a group's feed. It has a `group_id` and a `kind` so that events of groups (created, renamed, a member added) can join the same feed later; none is recorded yet (decided).
  - **Writers** (each in the same transaction as the change): `createExpense` inserts `added` (so a payment, which is created through it, too), `updateExpense` inserts `edited` with the list of changes (it still works the changes out from the version it loaded, ADR-039, but the version before is no longer stored: it is the previous event's snapshot), `deleteExpense` inserts `deleted` and `restoreExpense` inserts `restored`, both with the expense's current snapshot. The expense row stays the current state; the events are its whole history.
  - **Backfill:** the migration copies what exists, so no history is lost: an `added` event for every expense (who: `created_by`, when: `created_at`, snapshot: the first revision's `before` for an edited expense, the current state for one never edited), an `edited` event for every revision (snapshot: the next revision's `before`, or the current state for the last; changes as stored), and a `deleted` event for every expense deleted now (who: `updated_by`, when: `deleted_at`, snapshot: the current state). The current state is built in SQL from `expenses`, `expense_shares` and `expense_photos`.
  - **`expense_revisions` is superseded:** nothing reads or writes it any more. Its definition stays in `schema.ts`, marked as legacy, so that `drizzle-kit` does not generate a `DROP TABLE` by itself; a later migration drops it deliberately once the events have proved themselves.
  - **Restore:** `restoreExpense(db, userId, groupId, expenseId)` checks the user is a live member and the expense is in that group, then, in one transaction, clears `deleted_at`, sets `updated_at` and `updated_by` (so the group is active again, ADR-028) and inserts a `restored` event. It returns `{ ok: true }`, `{ ok: false, notFound: true }` (unknown, malformed, another group's, not a member) or `{ ok: false, notDeleted: true }` (the expense is live, for example restored by someone else a moment ago). Nothing else changes, so everything that leaves out deleted expenses (balances, recent currencies, the edit page) counts it again.
  - **Reading:** `getExpense` returns `history`, the expense's events newest first, each `{ kind, by, at, changes, currencyBefore }` (`currencyBefore` is the old currency of an edit, from its changes, else the snapshot's). The History section writes whatever the list holds, including the `added` entry, which replaces the one it built from `createdAt` (still returned); `lastEdit` comes from the newest `edited` event; `deleted` (who and when, from the row) is still the current state; `people` names everyone the changes refer to. The section is always shown (decided later: the user wanted to see who added an expense and when without it having been edited, and the band no longer says it).
  - **Page:** a deleted expense's header has a Restore button instead of Edit and Delete; it works at once (no dialog, restoring is harmless and Delete undoes it), is busy while it works, shows "Expense restored." (or "Payment restored.") and the page reads the expense again so it shows as a live one in place (`ExpensePage`'s `retry`, handed to `ExpenseDetails` as `onChanged`).
- **As built:** `expense_events` in `schema.ts` (with `EXPENSE_EVENT_KINDS` in `db/constants.ts`), migration `0007_expense_events.sql` (the generated table plus three hand-written `INSERT … SELECT` backfills: added, edited, deleted), and in `expenseService` `loadSnapshot` (the expense as stored, deleted or not), `recordEvent` and `loadEditable` (built on `loadSnapshot`), `restoreExpense`, and `getExpense` reading the events (sorted newest first, same-moment events kept in the order added, edited, deleted, restored). The History section writes every entry of `history` (`historyHeader(by, kind, noun)`), and the details page's `onChanged` is the page's `retry`, with `keepPrevious` so the page stays on screen while it reads again. Tests: `expenseEvents.test.ts` (events and restore at the service), the 0007 backfill test in `src/db/__tests__/schema.test.ts` (a database as it was before the migration), `src/pages/expense/__tests__/restore.test.tsx` and the restored-row test in the group page's `index.test.tsx`; the edit-page tests read the edit events.
- **Rejected:** a `kind` column on `expense_revisions` (its `before` snapshot means nothing for a deletion), keeping only `deleted_at` (a restored expense would lose its "You deleted…" entry), light events that carry only a title and an amount and point at a revision (the feed and restoring a version would need joins, and an old event would read differently after a rename), keeping both revisions and events written (every edit stored twice, two things to keep in step), asking before restoring, leaving the page after restoring, and recording group events now (more features and tests in this change).
- **Consequences:** a schema change (asked and approved). Every event stores a full snapshot, a few kilobytes, none ever removed. Any earlier version of an expense can be shown or restored from its events later. Sync (ADR-010) carries events like any row. A deletion on one device and a restoration on another between syncs are two events, and the newest `updated_at` on the expense row decides whether it is deleted; the history shows both. The Activity page can read `expense_events` (and later group events) sorted by `occurred_at`; which events are new to a user (an unread marker) is a separate decision.

## ADR-043: Versions of an expense, and going back to one
- **Context:** every event holds the whole expense right after it (ADR-042), so any moment of its history can be shown, and put back. The History entries should open a page with that version and offer to restore it.
- **Decision:**
  - **Schema (migration 0008):** `expense_events.kind` gains `reverted` (the check constraint is replaced; `EXPENSE_EVENT_KINDS` gains the value) and a new nullable column `restored_from` (a `uuid` referencing `expense_events.id`: the version that was put back). Both are added to the same table; nothing else changes and no row is rewritten.
  - **Reading a version:** `expenseService.getExpenseVersion(db, userId, groupId, expenseId, eventId)` returns the event (kind, who, when, changes, the old currency of an edit, and for a `reverted` event the time of the version it went back to), the snapshot in the shape the page shows (fields, each share with the person's name and whether it is the viewer, photos in order), the names everything refers to, and three flags: `isCurrent` (the snapshot equals the expense as it is stored now: same fields, same shares, same photos), `expenseDeleted` and `isPayment`. Null when the user cannot see it: unknown or malformed ids, an event of another expense, another group's expense, or a group the user is not in (all alike, as elsewhere). It works on deleted expenses and on payments.
  - **Going back:** `expenseService.restoreVersion(db, userId, groupId, expenseId, eventId)` in one transaction: checks membership; refuses a deleted expense (`{ ok: false, expenseDeleted: true }`) and a payment (`notFound`, like editing); finds the event of that expense; and refuses a version equal to the current one (`{ ok: false, alreadyCurrent: true }`). Otherwise it writes the snapshot back verbatim: the expense's fields; each share's paid, owed and entered value (a person with a share now and none in the snapshot gets 0 and 0, a person only in the snapshot gets a row); and the photos (rows in the snapshot that were soft-deleted are brought back, rows not in it are soft-deleted, positions renumbered; a row that does not exist at all is inserted from the snapshot). Shares are not worked out again: the version says what each person owed, and a member who joined since simply has no share in it. It sets `updated_at` and `updated_by` (activity, ADR-028) and records a `reverted` event whose snapshot is the restored state, whose `changes` are those from the previous state to it (as for an edit, `expenseChanges`) and whose `restored_from` is the version's event.
  - **History:** a `reverted` entry reads "You restored the version from 20 Oct 2026, 6:04 pm" with the lines of `changes`; `getExpense` adds `restoredFromAt` to its entries. Every entry is a link to its version page.
  - **Page:** `src/pages/expenseVersion` at `/groups/<id>/expenses/<expenseId>/versions/<eventId>` (`ROUTES.expenseVersion`), with a header (Back, "Version", the button), the entry line and its bullets, and the expense as it was. The pieces it shares with the details page move to `src/components` since two pages use them: the receipt gallery (`ReceiptGallery`, with its thumbnail) and the wording of the history lines and split (`historyLines`, `historyHeader`, `owedSentence`, `paidSentence`, `SPLIT_METHOD_LABELS`).
  - **As built:** migration `0008_expense_event_reverted.sql` (generated); `expenseService.getExpenseVersion`, `restoreVersion` and the pure `sameSnapshot` in `utils.ts`, with `historyEntryOf` and `peopleReferredBy` shared with `getExpense`, whose history entries now carry the event `id` and, for a reversion, `restoredFromAt`; a reversion counts as the expense's last edit (the "Edited by" line). The code moved so that two pages share it: `src/components/ExpenseBody` (the summary, split, notes and receipts, used by the details page, which puts its own lines in `before` and `after`, and by the version page), `src/components/ExpenseWording` (`displayName`, `paidSentence`, `owedSentence`, `SPLIT_METHOD_LABELS`, `historyHeader`, `historyLines`), `src/components/ReceiptGallery` and `src/components/HistoryEntry` (an optional `to` makes the whole entry a link, with an arrow). The page is `src/pages/expenseVersion` (`ExpenseVersionPage`, `VersionDetails`, `VersionNotFound`; the route `ROUTES.expenseVersion`), which reads again with `keepPrevious` after a refusal. - **Not asked:** restoring needs no dialog, since the version it replaces is itself in the history. The button is missing, with a line saying why, on the current version and on a deleted expense (it must be restored first, ADR-042); on a payment there is none.
- **Rejected:** saving a version-restore as an ordinary `edited` event (nothing in the history would say it was a restore), restoring a version and un-deleting in one step (two different actions), working the shares out again from the entered values (a version is what was true then, and the rounding or the members may differ now), asking before restoring, and opening only the adding and the edits (every event holds a snapshot, so every entry can be shown).

## ADR-044: Backup and group sync through Google Drive
- **Context:** ADR-008, ADR-009, ADR-010 and ADR-013 sketched backup and sync; nothing was built. The product decisions are in PRD 5.8; this records how. All six phases are built, see "Phase 1 as built" to "Phase 6 as built"; parts still marked "proposed" are confirmed when their phase starts.
- **Decision:**
  - **Drive layout:** one `OwnLedger/` folder in each user's My Drive, with `Backup/` (never shared) and `Groups/<group name>/` (shared with the group's members). Groups created by others are Drive shortcuts in `Groups/`. Rejected: group folders loose in the Drive root (clutter, and no single place to find or delete everything the app made). Every folder and file the app creates carries Drive `properties` (`ownledger` = `root`, `backup`, `groups`, `group`, `member-file` or `photo`; `ownledgerGroupId`, `ownledgerPersonId`, `ownledgerPhotoId`), and the app finds them by those, never by name. `properties` (not `appProperties`) because other members' apps must read them.
  - **Drive access:** the `drive` scope (ADR-009) is asked for on the first Sync press (incremental consent, ADR-019), through `useGoogleLogin` inside the click so popups are not blocked, and the token is held in memory as now (ADR-024). There is no refresh token, so sync is only started by a press: no automatic sync (decided; may come later while a token is still valid).
  - **Backup:** a JSON file in `Backup/` with every row of every table on the device (in the same zod-checked row format as the sync files), replaced on each backup, and every photo in `Backup/photos/`, uploading only the ones missing. Rejected: `pgDump` (ADR-008), because restoring it replaces the whole database and ties the file to one schema version, while a JSON copy can be merged into data already on the device and read by later versions of the app. All photos go in the backup, also those already in a group folder (the user chose a complete backup over saving Drive space). Every photo on the device goes, also those removed from an expense or on a deleted expense (decided), as originals only, the thumbnail being made again on restore (decided). Each is a file named by its photo id and tagged (`ownledger = backup-photo`, `ownledgerPhotoId`), in `Backup/photos/` (tagged `backup-photos`); the backup lists that folder once and uploads only what is missing, a few at a time, and never deletes from Drive (a photo never changes and is never removed on the device). A photo that fails is counted and the others carry on (decided); access running out stops the run. The device running out of space while restoring stops the downloads with its own message (decided); there is no size warning before a restore (decided). `sync_status` records the backup once the data is in Drive; the photos are their own step (`backUpPhotos`, `restorePhotos`), and failed ones only show on the dialog's line.
  - **Backup kept:** only the latest file, replaced in place (decided); a restore merges, so older copies add little.
  - **Restore:** (removed in phase 6: every full Sync merges the backup in instead) only from the avatar menu ("Restore from Drive", decided), never offered by itself, and it runs without a confirmation (decided: it removes nothing). It merges with the rules below, then downloads missing photos.
  - **Group file (ADR-010, refined):** `OwnLedger/Groups/<group name>/<email>.json` (first `<personId>.json`; see "Member files by email" below), tagged `ownledger = member-file` with `ownledgerGroupId`, `ownledgerEmail` and `ownledgerPersonId`: `{ app: 'ownledger', kind: 'group', format: 1, groupId, writtenAt, writtenBy, rows }`, the rows in the backup's format. Each file still has one writer, but it holds **the whole group as that device knows it** (the group, every membership, expense, share, photo row and event, deleted ones included, and every person those rows name), not only the rows its writer changed last as ADR-010 first said. Merging newest-wins makes the overlap harmless, and the group survives when a member's own file is gone (they left, or deleted it) and when a person was last changed by someone outside the group (such a person row would otherwise be in nobody's file). It costs size, small for a group of friends. Nobody else known on the device is written (only the people the group's rows name). Validated with zod; a file that fails is skipped and reported. The same account on two devices writes the same file: each device reads it first like any member's, so what one wrote reaches the other before it is overwritten (two exactly simultaneous syncs can lose one write until the next sync).
  - **Reading a member's file:** only rows of that group are taken (the group itself, its memberships and expenses, their shares, photos and events, and the people those rows name); anything else in the file is ignored, so a file cannot change other groups or people. Files are not checked against their Drive owner: any member may change anything in the group anyway (ADR-011).
  - **Merge (proposed):** per row, newest `updated_at` wins, `updated_by` breaks a tie. `expense_events` are insert-only, so they are unioned by id. `group_members` (group + person) and `expense_shares` (expense + person) also merge by that natural key, so two devices that made a row for the same pair end with one. A pure function, unit-tested.
  - **One person per email (proposed):** each device makes its own person ids, so the same email can arrive under two ids. On import they are merged into the smaller UUID, so every device picks the same one, with `userService.mergePeople` (ADR-035); the device record's person id follows when it was the user's. People without an email are never merged. The local rule that names are unique (ADR-034) is not applied to people who arrive by sync.
  - **Who creates the folder (decided):** only the group's creator, on their first sync of it, so two members never create two folders at once. Other members' Sync of the group waits ("Waiting for Omkar to sync this group first."). Any member shares the folder (Drive `writer`, with Drive's notification email, decided) with members who have an email and are not shared yet. Members without an email are synced as people but not shared the folder (decided).
  - **Finding shared groups:** Drive cannot notify a client-only app (its push notifications need a server, ADR-001). A full Sync lists folders shared with the user that have `ownledger = group`, imports every one whose group is not on the device, and adds the shortcut (tagged `group-shortcut` with the group id, in the user's `OwnLedger/Groups`). The progress dialog lists them; there is no other hint (decided). A folder whose files do not make the user a member is left alone.
  - **Folders and names (decided):** every group gets its folder on Sync, even with nobody to share with. The creator's sync keeps the folder's name equal to the group's.
  - **Pending (decided):** a member is no longer Pending once this device has read their own file in the group's folder. That is remembered in `sync_status` under the scope `member:<group id>:<person id>` (with the file's `writtenAt`), so no new table is needed; `group:<group id>` holds the group's last sync, shown on the band's Sync button.
  - **Errors (decided):** a group that fails shows Drive's own reason (status and Google's message) after "Couldn't sync this group. Press Sync to try again."; the other groups carry on.
  - **Order and resuming (ADR-013):** download and merge others' data (committed), upload the user's own file, then photos (upload missing, download missing). Each step is idempotent, so a second press carries on. Running out of Drive access stops the run cleanly.
  - **Local-only state (decided, a schema change approved):** a PGlite table (not `localStorage`, so it goes with the data when that is cleared), `sync_status` (migration 0009): the time the last backup (scope `backup`) and, later, each group's sync (`group:<id>`) finished. It is not synced or backed up, so it has none of the sync columns. Drive ids are not stored: the folders and files are found by their tag on every run (one small query each), which keeps working when someone moves, renames or deletes them in Drive; a stored id would go stale then.

  - **Names from Google give way (decided):** `userService.resolve` used to set the user's own person's name to their Google name on every sign-in with the current time, so the name a member typed for them ("Sam") lost the newest-wins merge to their Google name ("Samuel") on every device after their first sync, and two people could end up with one name. Decided: a typed name always wins. A name the app takes from Google (a new person at sign-in, a guest who signs in, a person saved with no name) is written with `updated_at` at the Unix epoch (`GOOGLE_NAME_TIME`), so any version someone typed is newer and wins the merge (`isNewer`); a person whose row is still at that time has only a Google name, and a changed Google name replaces it (still at that time); a person with a typed name keeps it, whatever their Google name. The same holds on the person's own device: their own row reads the typed name once they have synced. The epoch is the marker, so no column is added. Rejected: names that differ per device, like phone contacts (a schema change, and a choice of which name others see), letting the Google name win (the user's report), and only skipping the rename at sign-in (the person made at sign-in on a fresh device is newer than the typed name and still won). Two people with one name are allowed (decided): the members sheet and pickers show each email.
    - **As built:** `userService.resolve` and `GOOGLE_NAME_TIME` in `userService/constants.ts`. Tests: `userService/__tests__/index.test.ts` (a new person and a signed-in guest get the weak time, a typed name is kept and a Google-only name follows the account) and `syncService/__tests__/groups.test.ts` (Priya added as "Sam" signs in as "Samuel" on her own device; after both sync, both devices call her "Sam").
  - **The backup stays complete (tests):** `backupService/__tests__/completeness.test.ts` reads the tables and columns from the database itself (`information_schema`), so a table or column added later fails the tests until the backup handles it. It checks that the test data fills every column of every table at least once (so the round trips see real values, not only nulls), that the backup has every table except those listed in `NOT_BACKED_UP` with their reason (`ownledger_migrations`, `sync_status`, the legacy `expense_revisions`), that every column of every row survives being written as JSON and read back through the zod schema, history snapshots included, that it holds every row (people in no group and deleted rows included), that importing it into an empty device gives back every row exactly, and that a member's group file has rows of every table and brings them back exactly. A new table therefore needs data in that test, a place in `exportAll`, `exportGroup`, the file's schema and the merge, or a line in `NOT_BACKED_UP` saying why it is left out. Break-checked by leaving a table out of `exportAll`, `exportGroup` and the merge, dropping a column and a snapshot field from the schema, and adding a table and a column in a temporary migration.
- **Dev server and the open database:** a hot update of `src/db` (the schema, or a new migration file) loads a second copy of `client.ts` whose `current` is empty, next to the first, which holds the open database; every page then fails with "The database is not open. Sign in first." until a reload (found when an app installed from the dev server in the simulator failed to open a group while files were being edited). `client.ts` reloads the page when a second copy of it is evaluated (`import.meta.hot` only; production is unaffected). Not unit-tested: jsdom has no hot reloading.
- **Rejected:** a sync button per group only (the backup would fall behind), automatic sync (needs a token without a press), sharing without Drive's email (members would not know to press Sync), refusing to sync groups with members who have no email.
- **Consequences:** a member's own file and photos are owned by them and count against their Drive storage; the group folder is owned by its creator, and if they delete it the group's shared copy goes (the ownership open question in the PRD). Merging relies on device clocks (ADR-010). A full sync with many photos can be slow; the photo warning comes with phase 4. Real Drive tests need the OAuth client ID, which does not exist yet (PRD open questions).

## ADR-045: Group members page, local names and editing a pending person's email
- **Status:** built and tested.
- **Context:** people could only be added in dialogs inside Create group and a group's members sheet (ADR-034, ADR-038). There was no place to see everyone saved on the device, fix a wrong name or give a Pending member an email.
- **Decision:**
  - **Page:** `src/pages/members` at `/members` (`ROUTES.members`), opened from a "Group members" item in the avatar menu (`AppHeader`). It lists `groupService.listKnownPeople` (everyone but the user) and reuses `AddMemberDialog` (ADR-034). Behaviour and copy are in PRD 5.9.
  - **Schema (migration 0010, approved):** `people.local_name` (nullable text). It is a device-private label: it is **not** in the sync rows of group files and does not travel with a person. It **is** in the backup (a personal copy of everything on the device), and `NOT_BACKED_UP` and the completeness test (ADR-044) need it handled in `exportAll`, the schema and the merge, but excluded from `exportGroup`. A local name has no `updated_at` of its own: backup merges follow the person row's newest version.
  - **Display:** one rule, `displayName(person)` = `local_name` when set, else `name`, else the email's first part, used by every screen that names a person (services return it, so no screen has to choose). The shared `name` and its newest-wins merge (ADR-044, "Names from Google give way") are untouched.
  - **Uniqueness:** a local name must not equal another person's shown name on the device (ADR-034's rule, applied to shown names). A shared name that arrives by sync may still clash (ADR-044): both are kept, with their emails.
  - **Email:** editable only for a person who is Pending in every group (`syncedMembers` empty, ADR-044) with `personService.updateEmail`; it validates like `addPerson`, refuses an email another person has (naming them), and sets `updated_at` and `updated_by`, so it syncs and the next sync shares the folder. No merge of two people.
  - **Service:** `personService.updatePerson(db, userId, personId, { localName, email })` returns field errors like `addPerson`; `{ ok: false, notFound: true }` for an unknown person or the user themself.
- **As built:** the page is cards (`MemberItem`, the whole card opens `EditMemberDialog`, with a "Pending" tag), and the local name is required ("Enter a name."; a name equal to the shared one clears the local name). `shownName(table)` in `src/db/shownName.ts` is the one SQL expression for the shown name, used by every query that selects a person's name. `personService.listManaged` and `updatePerson`. The backup carries `local_name` (`exportAll`) but `exportGroup` strips it, and the merge's `keepOwnDetails` pass restores it after a newer person row replaced the row (a version from another device never takes it away). The page gives the edit dialog a new `key` for each opening, so its form starts from what the person has now (an Ant Design form keeps what was typed in it after it closes; the first fix, `preserve={false}`, did not hold). Tests: `personService/__tests__`, `backupService/__tests__`, `pages/members/__tests__` and the menu tests in `AppHeader/__tests__`; break-checked by 28 deliberate breaks, all caught.
- **Rejected:** renaming for everyone through sync (the user wants a private label, and a shared rename would fight the Google-name rule), showing the local name only on the new page (one person with two names on one device), merging people on an email clash. (Leaving the user out of the list and not letting them edit their own name was rejected here at first and reversed later: see the addendum.)
- **Addendum (the user's own card, the email always shown):** `listManaged` now includes the user, first (`isYou`, never `pending`), and the page tags the card "You" where others have "Pending". `updatePerson` accepts the user's own id for a local name (uniqueness as for others) and ignores any email sent for them: their email is their Google account's. The edit dialog always shows the email: enabled only while the person is Pending, switched off otherwise with a note (`emailNote`); the page's "No members yet." now means nobody besides the user. Tests: `personService/__tests__` (the user listed first, never pending, own name, email kept, a clash), `pages/members/__tests__` (order, tag, dialog states, own card). Break-checked by 12 deliberate breaks, all caught.
- **Consequences:** a schema change (approved). Every query that selects a person's name must go through the display rule. A person with a local name still syncs under their shared name, so another member never sees the label.

## ADR-046: Google pictures for people
- **Context:** only the signed-in user's avatar showed a picture (from the session); everyone else was an initial.
- **Decision:**
  - **Schema (migration 0011, approved):** `people.picture`, a nullable text holding the address of the Google profile picture. It is in the backup and in group files like any column (the zod schemas leave it optional so older files still read). Google pictures are not behind a login (an unguessable public address), so sharing the address shares no more than the person's Google account already does; members see each other's emails in the same files.
  - **Written by the person's own device:** `userService.resolve` saves the account's picture on the user's person when it differs. It does **not** touch the row's `updated_at`, because the row is merged whole and a newer time would let this device's version of the name beat a name someone typed (ADR-044, "Names from Google give way").
  - **Merge:** `keepOwnDetails` (ADR-045) also fills `picture` after a merge: a person's picture is kept from before, or taken from the incoming row, whichever exists, so a newer row written by someone who never saw it cannot empty it. Rejected: a per-field timestamp (a schema change). Limit: with no time of its own, a changed Google picture reaches a member who already holds the old address only when that person's row is next replaced by a newer one (PRD open question).
  - **Showing it:** `PersonAvatar` (`src/components/PersonAvatar`) replaces the initial-only avatars of people (members page and sheet, add-a-member list, split dialog, expense split); the user's own header avatar keeps `ProfileAvatar`. Services return `picture` with each person (`GroupMember`, `KnownPerson`, `ManagedPerson`, `ExpenseShareDetails`).
  - **Offline copy (removed, see below):** `usePersonPicture` used to keep the image in the photo store under `person-picture:<address>`. It is gone: `PersonAvatar` shows the address itself and falls back to the initial when the image fails.
- **Offline copy does not work for most pictures (found later, decided):** Google serves pictures people uploaded themselves (`lh3.googleusercontent.com/a-/…`) with no `Access-Control-Allow-Origin` header, so `fetch` from the app fails with a CORS error (checked from the page and with `curl` for the origins `localhost:5173` and `omkarsheral1989.github.io`) and no copy is made; only some pictures (default avatars) allow it. The `<img>` tag needs no CORS, so online the picture shows from the address. Offline the avatar shows only while the browser's HTTP cache still holds the file (Google answers with `cache-control: public, max-age=86400`, so a picture loaded in the last day usually does; checked on a default avatar, not on an uploaded one) and otherwise falls back to the initial (`PersonAvatar`). Accepted. Rejected: caching the pictures as opaque `no-cors` responses in the service worker's cache (shows offline, but Chrome pads each opaque response to about 7 MB of quota, and the content cannot be checked), and a proxy (needs a server, ADR-001, ADR-018). `usePersonPicture` and its download were removed (it logged a CORS error in the console for each picture and only worked for the few pictures that allow it); copies already saved under `person-picture:` stay in the photo store unused, and nothing syncs or backs them up.
- **Rejected:** a picture only for the signed-in user (nothing for others), re-downloading on every view (not offline), sending the image bytes through Drive (more sync work for a picture each device can fetch itself).
- **Consequences:** a schema change (approved). A person has no picture until their own device has signed in with Google and synced. Tests: `PersonAvatar/__tests__` (the address, no referrer, nothing downloaded, the initial as a fallback), `userService`, `backupService` (kept, filled, never replaced), a two-device sync in `syncService/__tests__/groups.test.ts`, and the avatars in the members sheet, add-a-member list, expense split and split dialog.

## ADR-047: Receiving shared pictures (Web Share Target) with our own service worker
- **Context:** the user wants to share a receipt photo from any app to OwnLedger. The Web Share Target API lets an installed PWA appear in the share sheet; a file share arrives as a `POST` with `multipart/form-data` to a URL of the app, and a static site has no server to answer it, so a service worker must. iOS does not implement the API (no share target in Safari or installed web apps), so the feature is Android and desktop Chrome or Edge only (PRD 5.11).
- **Decision:**
  - **Service worker:** `vite-plugin-pwa` moves from `generateSW` to `injectManifest` with our own `src/sw.ts`. It keeps everything the generated worker did (precache of the build, `cleanupOutdatedCaches`, the navigation fallback to `index.html`, the `registerType: 'prompt'` update flow through a `SKIP_WAITING` message) and adds one `fetch` handler for the share address. Its types live in `tsconfig.sw.json` (the `webworker` library cannot share a program with the DOM library of the app).
  - **Manifest:** `share_target` with action `/ownledger/share-target`, method `POST`, `multipart/form-data`, the file field `receipts` (`image/*`) and the `title`, `text` and `url` fields.
  - **Handler:** `receiveShare` (`src/pwa/shareTarget.ts`) reads the form data, keeps up to 10 pictures (anything that is not an image is ignored), builds the notes' text, saves both in a small IndexedDB database of their own, `ownledger-shared` (`src/pwa/sharedFiles.ts`, one record, replacing an earlier one), and answers with a 303 redirect to `/ownledger/share`. It never fails the navigation: a broken share still redirects, to the same page, which then finds nothing.
  - **Landing page:** `/share` (`src/pages/share`, inside the signed-in layout) reads the held share, picks the user's most recently active group (`listGroups`, ADR-028), clears the held share and `navigate`s with `replace` to that group's add-expense page with an `ExpenseDraft` in the router state (the carry-over of the group switcher, ADR-031, reused: receipts as `File`s, notes, the default currency of the group). So Back asks to discard, and the form needs no new code. A held share is read once (a ref guards React's double effect in development). Signed-out visitors never reach it: `RequireAuth` takes an `onDenied` callback, which `App` uses to remove the held share, and then sends them to the welcome page. A share older than an hour is ignored and removed.
  - **Dev:** the worker is off in development, so `devOptions.enabled` follows the `SW_DEV=true` environment variable, and a development-only route `/share-test` has a plain form that posts to the share address.
- **Rejected:** keeping `generateSW` (it cannot add a `fetch` handler for a POST except through `importScripts`, which the plugin makes awkward to type and test); a Cache API entry instead of IndexedDB (the app's data layer is IndexedDB already, and the files are small records); asking the user to choose the group on a page of its own first (one more step; the group dropdown already switches); native iOS wrapper (an App Store app and an Xcode project, against ADR-001).
- **Consequences:** the worker is now our code, so Workbox upgrades are ours to follow; the duplicate-precache check in `scripts/deploy-pages.sh` still applies (the injected manifest keeps the `url:"…"` form, checked after the build). Anyone with the app installed gets the new worker through the existing update prompt, and Chrome only offers OwnLedger in the share sheet once the installed app has the new manifest. Shared pictures live on the device only between the share and the page opening (privacy: ADR-018 holds, nothing leaves the device).

- **Found after the first deploy (share gave "405 Not Allowed"):** GitHub Pages runs Jekyll, which does not serve files whose names start with `_`. The build had a chunk `assets/__vite-browser-external-….js`, listed in the precache but a 404 on Pages, so the worker's install (it caches every file) failed and no worker ever ran: the share POST reached the server (405), and no update prompt appeared. Fix: `vite.config.ts` strips leading underscores from chunk names (`chunkFileNames`), and `scripts/deploy-pages.sh` refuses to deploy when `dist` holds any `_`-prefixed name. Rejected: a `.nojekyll` file in the Pages repository (it changes the other apps' hosting). The worker's behavior later moved to `src/pwa/workerHandlers.ts` with `src/sw.ts` as wiring (ADR-049). Checked by fetching every precached URL from the live site. The deploy's checks moved into `scripts/checkDist.ts` (ADR-049).

## ADR-048: Logging to the browser console
- **Context:** the app wrote nothing to the console, so a failure on a phone or in the installed app (the share gave "405" and the worker silently never installed) could only be guessed at. The user asked for enough logs to debug from DevTools.
- **Decision:**
  - **One logger,** `logService` (`src/services/logService`): `logService.scope('sync')` gives `debug`, `info`, `warn` and `error`. Every line is `[ownledger:<scope>] message` with an object of plain fields, so the console can be filtered by "ownledger" or by a scope. It also runs in the service worker (its console is under DevTools, Application, Service Workers).
  - **Levels:** `info`, `warn` and `error` are always shown. `debug` lines (each Drive request, closing the database, reusing a token) show only with the flag: `localStorage.setItem('ownledger-debug', '1')` (kept) or `?debug=1` in the address (one visit). Read at each call, so it works without a reload. Rejected: everything always on (noisy), and nothing without the flag (errors would be missed).
  - **Privacy (PRD 5.12):** logs stay in the user's own console, but they may be pasted into a bug report, and the welcome page promises privacy. So no personal data is logged: ids, counts, statuses, timings and error reasons only. The logger enforces it: text under a field named like a personal one (`email`, `name`, `note`, `description`, `picture`, `text`, `title`, `url`, `address`, `phone`, `label`) is dropped (a count under such a name, `pictures: 2`, is kept), anything under `amount`, `cost`, `price`, `token`, `password` or `secret` is dropped, objects are reduced to their type and lists to their size, and emails and Google tokens inside any text are replaced by `[email]` and `[token]`. Because a field named `name` is dropped, a log field that holds a file name uses another key (`file`). Rejected: logging names and emails to help debug sync between members (the user chose no personal data).
  - **Where:** the service worker (started, installed, activated, share request, update accepted), the share target and page (counts, where the share went), the database (opened with its time, locked by another tab, failed, each migration applied), sign-in and Drive access (signed in or out, guest, access granted, window closed, wrong account), every Drive request (debug; each retry and failure at warn), the sync run (each step with counts, the failure that stops a run, start and end with time), and the actions of the expense, group and person services (one line each with the ids, how it ended, and the time: info when it worked, warn when it was refused, error when it threw). The service actions are logged by `logService.logActions`, which wraps the listed functions of a service (`expenseServiceBase` is the object as written, `expenseService` the wrapped one) so no function body changes. Uncaught errors and rejected promises are logged by `watchGlobalErrors(window)` in `main.tsx`; the app logs its start (mode, online, installed) and the connection going and coming.
  - **Tests stay quiet:** `src/testing/setup.ts` silences the output; a test reads the lines with `captureLogs()` (`src/testing/logs.ts`). Every place that logs has a test for its lines, and the ones that handle personal data assert that none of it appears.
- **Consequences:** a refactor that drops a log line fails a test, which is intended: the lines are how the app is debugged. A new action in the three services needs an entry in their `logActions` call; the other services (backup, sync) are logged from `useSync` and the Drive client.

## ADR-049: Tests that guard against breaking the app while refactoring

A 94.6% line coverage run (`@vitest/coverage-v8`, a dev dependency now) showed the gaps were the wiring: the service worker, the update prompt, `useDatabaseSession`, the database client and lock, the install hook, and `App.tsx` and `main.tsx`.

- **Consequences:** `bun run test` is about 10% longer. The journeys depend on visible text, so changing copy means updating them (and the PRD) together.

## ADR-051: Pages remember what they read (TanStack Query)
- **Context:** every page read the database each time it opened and started at the loader, so going home, into a group and back showed the loader twice, though the data was on screen a moment before.
- **Decision:** `@tanstack/react-query` (the user chose it over a small cache of our own and over hand-written stores) keeps the last result of each read-only page in memory.
  - **`useCachedData(load, key, { keepPrevious })`** (`src/hooks/useCachedData`) has the states and `retry` of `useAsyncData`, over `useQuery`. The first visit to a key is `loading`; later visits are `ready` at once with the earlier data, while the page reads again behind it and updates if the result changed. Used by home, the group page, the expense page, a version and the members page. Forms (add expense and settle up changed in ADR-060, edit expense and edit group in ADR-055) and small readers (photo tiles, the sync dialog, the database gate) keep `useAsyncData`, so a form never opens with values that are about to change. `retry` joins a read already running (`cancelRefetch: false`), so a change that refreshes a page and the page's own retry are one read.
  - **Settings** (`createQueryClient`): `networkMode: 'always'` (the data is on the device, so it reads offline; the default would pause every read without a connection), no retries (a failure is shown, with Try again), `staleTime: 0` (always read again when a page opens), `gcTime: Infinity` (kept until the app closes), no refetch on focus or reconnect.
  - **Staying true** (`QueryProvider`, wrapping the app in `main.tsx` and every page in `renderPage`): the database has no change events, so `dataChanges` (`src/db/changes.ts`) announces them: `notifyAfter` wraps the writing functions of the expense, group and person services (outermost, after logging) and announces after each call that worked (a refused call, or a throw, announces nothing), and a finished sync announces. On an announcement the pages on screen refresh in place, and the ones not on screen are forgotten, so their next visit shows the loader once and then fresh data (never a stale screen after a change). Signing in or out, or starting guest mode, forgets everything (`client.clear()`); the user's id is also in every key.
  - **Keys (bug found after release):** the home page and the members page both used `userId:dataVersion` as their key, so the members page showed home's remembered groups and crashed to a blank screen. `useCachedData(load, page, key)` now takes the page's name as its own argument and builds the query key from both, so two pages can never share an entry.
  - **Cost:** after a write, a page the user then opens shows the loader once. The first visit to anything, and the first load after the app starts, show it too. Prefetching (for example a group on hover) is not done.
- **Rejected:** keeping every remembered page and refreshing it all after a write (a stale flash on pages the user opens next, or many reads for pages never opened), `staleTime` above 0 (a page could show data from before a change made by another tab or a sync), persisting the cache to disk (the data is already local), and caching forms.
- **Tests:** `useCachedData/__tests__` (first visit, coming back, keys, `keepPrevious`, errors and retry, offline, kept while idle), `QueryProvider/__tests__` (refresh in place, forgetting, who is using the app), `db/__tests__/changes.test.ts`, `announces.test.ts` of the expense and group services, `useSyncStore/__tests__`, and `src/__tests__/navigation.test.tsx` (home and group page come back at once with every read slowed down, and show new data after a change). Changes that arrive from another device or tab are simulated with `fromElsewhere` (`src/testing/changes.ts`), since a change made through a service on this device refreshes the pages by itself. Break-checked: each setting, the key, `keepPrevious`, the refresh and the forgetting, the announcing (success, refusal, sync) and each page's use of the hook.

## ADR-052: Pages open with what the previous page already knew
- **Context:** opening a group from the home list showed only a loader on its first visit, though the list already knew the group's name, type, currency and number of members, all the colored band needs.
- **Decision:** the home row's link passes `{ group: { id, name, type, defaultCurrency, memberCount } }` as router state (`GroupPageState`, `KnownGroup`). The group page reads it with `knownGroupFrom(location.state, id)`, which accepts it only for the same id with every field of the right type (anything else, such as a direct link, gives nothing). ## ADR-055: A sync blocks the app, Stop, and edit pages that open at once
- **Context:** the user found a loader when pressing Edit on an expense, though the expense page has what the form needs. The only way the data could change under an open form was a sync that keeps running behind a closed dialog (one tab only, ADR-026), so the sync was made blocking.
- **Decision:**
  - **Blocking sync:** `AdaptiveDialog` has `dismissible` (default true): false removes the close button and ignores a click outside and Escape (`closable`, `maskClosable`, `keyboard`); the mask dims the app behind (the normal modal look). `SyncDialog` passes `dismissible={!running}`, and its footer shows Stop instead of Close while a run goes on.
  - **Stop:** the run makes an `AbortController` and gives its signal to the Drive client (`driveService.client(token, { signal })`); `useSyncStore` holds `stopRun` and `stopping` (`requestStop` aborts and shows "Stopping…"). An aborted request throws `DriveStopped` (never retried), which `stoppingProblem` names `'stopped'`, so it stops the run like the other three failures: the line says "Stopped. Press Sync to carry on." and the Backup line "Not backed up: the sync stopped." Every step is repeatable, so the next Sync carries on. No Continue (only Drive access running out offers it).
  - **Timeout:** every Drive request is cut after `REQUEST_TIMEOUT_MS` (2 minutes, `AbortSignal.timeout`, combined with Stop by `AbortSignal.any`) and counts as a dropped connection (`DriveError` status 0). Without it a hung request would lock the app behind the dialog. Two minutes leaves room for a large photo on a slow connection.
  - **Edit pages:** `useCachedData(load, page, key)` is used by Edit expense and Edit group, and `prefetchCachedData` lets the page before them read their data: the expense page (not for a deleted expense or a payment) and the group page prefetch under the edit page's own `page` and key (`editExpense/utils.ts`, `editGroup/utils.ts`: `loadExpenseToEdit`, `loadGroupToEdit`, one loader each shared by both pages). The edit page then finds the data read, or being read. A change announcement (ADR-051) forgets what the edit page remembered once it is off screen, so Back to an old edit page after saving reads fresh; the expense and group pages read it again after a change.
- **Rejected:** a re-read behind the form with a "changed meanwhile" warning (nothing can change meanwhile once sync blocks), passing the data in router state (it survives browser Back to a stale form), an exit-less dialog with no Stop (a hung sync would lock the app), and a timeout alone (the user could not leave a slow sync).
- **Consequences:** Edit expense and Edit group no longer re-read fresh when opened from their page. The save-time checks remain: `updateExpense` and `updateGroup` still refuse a deleted expense or group. Closing the dialog while a sync runs is no longer possible, so ADR-044's "can be closed while sync goes on" no longer holds.
- **Tests:** `driveService` (signal, stopping, timeout), `useSyncStore` (stopping), `AdaptiveDialog` (staying and closing, phone and wide), `SyncDialog` (Stop, Close, cannot be dismissed), `groupSync.test.tsx` and the group page's `sync.test.tsx` (Stop ends the run with the lines), and `pages/__tests__/editOpensAtOnce.test.tsx` (no loader with the database stopped, the direct link, a payment). Break-checked on each option, each store field, the signal, the timeout, the stopped problem and message, and each page's prefetch.
- **Addendum (ADR-060): Add expense and Settle up too.** They now read with `useCachedData` (`ADD_EXPENSE_PAGE`, `SETTLE_UP_PAGE`, loaders in their pages' `utils.ts`), and the group page prefetches them with Edit group, for the same reason (a sync blocks the app); a pill that grows into their page needs the form there at once. Their other ways in (a direct link, a shared receipt) read as before. A page that changes the data and then goes to the group reads the group page first (`refreshGroupPage`), so it never comes back with its loader.

## ADR-057: Page transitions with the View Transitions API
- **Context:** page changes were instant. The user wants each change animated like a phone app (PRD 5.15).
- **Decision:**
  - **Mechanism:** the browser's View Transitions API (`document.startViewTransition`), which keeps a picture of the old page and the live new one and lets CSS animate them (`::view-transition-old(root)` and `::view-transition-new(root)`), so the old page can slide out a little and dim while the new one slides in. React Router can start a transition for a navigation (`viewTransition` on `navigate` and links); whether that works with the app's `BrowserRouter` (not the data router, ADR-027) is to be checked first, and if it does not, a small wrapper around `navigate` starts the transition itself.
  - **Direction:** the app sets `data-nav="forward"` or `"back"` on `<html>` before the transition and the CSS reads it (`src/index.css`). `useAppNavigate` (`src/hooks/useAppNavigate`) replaces `useNavigate` everywhere and takes `{ direction }` (forward by default; back for the Back arrows, Cancel, Save and Delete that return, the discard confirmations and the "load error" and "not found" screens); `AppLink` is the `Link` that does the same for a click (a modified or middle click is left to the browser). A `replace` navigation has no direction and is not slid. The router's own `viewTransition` option exists only for the data router, so the app starts the transition itself: `navigate` runs inside the `startViewTransition` callback, which returns a promise that `PageTransitions` resolves from a layout effect once the new page is committed (a 1 s timeout lets go of a page that never arrives).
  - **Fallback:** `PageTransitions` (rendered once in `App`) fades the `#root` element in (`element.animate`, `PAGE_FADE_MS` 200 ms) for every page change that is not a slide: no `startViewTransition` and a replaced page. With `prefers-reduced-motion: reduce` neither the slide nor the fade runs (JS and a CSS media query). The duration, distance and dimming are constants in one place (`src/theme/transition.ts`).
  - **Scope:** all routes, signed in or out; not the first render, and not dialogs or drawers (Ant Design animates those).
- **The browser's Back and Forward slide too (`installSlideOnBrowserBack`, `src/hooks/useSlideOnBrowserBack`):** the address changes first and the router replaces the page in the same event, so a transition started from a `popstate` listener found the new page already on screen and nothing slid (first tried: it faded instead). The listener now holds the event back (`stopImmediatePropagation`), starts the transition (the browser takes its picture of the page still on screen), and inside the transition's callback dispatches the same `popstate` again for the router (a `replaying` flag lets that one through), after which `PageTransitions` resolves the callback's promise as for a link. It has to be added **before the router exists** (`main.tsx` calls it first): the router's own listener was added earlier and ran first when this one was added later, even in the capture phase. Direction: the router's `history.state.idx` against the one of the page on screen (`slide.index`, kept by `PageTransitions`, with `slide.path`); a popstate that leaves the pathname unchanged (a #fragment) and a device that cannot slide (no View Transitions, reduced motion) are left to the router. Checked by the owner on a real iPhone (October 2026): the slides work. Other phones' own swipe-back animations were not checked. The Navigation API was not needed.
- **Rejected:** an animation library such as Framer Motion (a large dependency for what CSS does, and it needs the old page kept mounted while the new one mounts), animating only the new page (no sense of depth, and Back would look like Forward), and one fixed header with sliding content (the pages' headers and bands differ).
- **Risks to test in the browser and the iPhone simulator:** a transition picture of a page with a fixed floating button, the safe-area padding at the top, scroll position of the page that comes back, and a page that is still loading when it arrives (the page cache of ADR-051 makes most arrive filled).
- **Tests:** jsdom has no View Transitions, so `src/testing/viewTransition.ts` stubs `startViewTransition` (and `prefers-reduced-motion`): `useAppNavigate/__tests__` (direction, default, replace, no API, reduced motion, state), `PageTransitions/__tests__` (no fade on the first screen, the fade, a slide waiting, reduced motion, the CSS variable), `useSlideOnBrowserBack/__tests__` (jsdom's `history.back` and `forward` with a held transition: the old page stays until the browser has its picture, direction, a #fragment, no View Transitions, reduced motion, removal), `AppLink/__tests__` and the journeys in `src/__tests__/transitions.test.tsx` (forward into a page, back through each Back path). How it looks is checked in the browser pane. Break-checked by 32 deliberate breaks, all caught (the call in `main.tsx` is wiring that no test reaches).
- **Addendum: 600 ms.** The slide took 300 ms (`PAGE_TRANSITION_MS`); it now takes 600 ms, like the pieces that travel between pages (`GROUP_OPEN_MS`, ADR-060), so every page change lasts the same (the owner's choice, October 2026). The easing stays the slide's own (a quick start, `cubic-bezier(0.2, 0.8, 0.2, 1)`); the fade of a page that arrives without a slide stays 200 ms (`PAGE_FADE_MS`). No test held the number: they read the constant.
- **Addendum (ADR-060): scroll positions.** The pages share the window's scroll, and the browser's own restoring ran after the transition took its picture (or not at all), so a row that a band shrinks back into was off screen. The app does it itself: `history.scrollRestoration` is `manual` (`installSlideOnBrowserBack`); `rememberScroll()` saves `window.scrollY` under the history position being left (`slide.scrolls`), called by `useAppNavigate` and the `popstate` handler; and `PageTransitions`, when the new page is committed and before the transition's picture, scrolls to the saved position for a pop (Back and Forward, the app's Back arrows included, ADR-059) and to the top for anything else. A reload starts at the top. Tests: `PageTransitions/__tests__/scroll.test.tsx` (`setup.ts` gives jsdom a `scrollTo` that moves `scrollY`).

## ADR-058: The group's expenses are read in batches
- **Context:** the group page read every expense of the group and drew a row for each. With hundreds of expenses that is a long first read (about 15 s the first time in the iPhone simulator) and hundreds of rows mounted at once.
- **Decision:**
  - **Keyset paging, 30 at a time:** `expenseService.listExpensesPage(db, userId, groupId, { limit, after })` returns `{ items, next }` (`ExpensePage`; `listExpenses` stays as it was and returns every row, for the sync tests and other callers; both use one reader, `readExpenses`): up to `limit` rows in the list's order (`date`, `created_at`, `id`, newest first) that come after the cursor, and `next`, the cursor of the last row, or null when there is nothing more (it reads `limit + 1` rows to know). The cursor is `{ date, createdAt, id }` with the creation time kept as the database's text (a JavaScript date would round it to the millisecond, and rows within a millisecond of each other, such as those made by `now()`, would be skipped), compared as a row (`(date, created_at, id) < (…)`), so two expenses on one day, or added in the same instant, never repeat or vanish between batches (offset paging would, when rows are added). The shares, payers and deleters are read only for the rows of the batch. `EXPENSE_PAGE_SIZE` is 30 (`expenseService/constants.ts`).
  - **The balances stay whole:** `groupBalances` and `balancesByGroup` read all shares and are unchanged, so they do not depend on what is shown.
  - **The page:** the group page's cached read (ADR-051) holds the first batch, so a page opened again starts at the first 30 (decided). Further batches are held by the page (`useExpenseBatches` in `src/pages/group/hooks`: rows, cursor, loading, failed; the page's list, `ExpenseList`, watches a sentinel under its last row), start empty when the first batch is read, and are added when a sentinel under the list comes within a screen of the view (`IntersectionObserver`, root margin about a viewport). A read that is already running is not started again. A failure keeps the rows and shows a "Couldn't load more." row with Try again.
  - **Reading again:** after a sync of the group or a member added (`retry`, `dataVersion`), the page reads `max(30, rows shown)` rows from the start in one query and replaces what it holds, so the list keeps its length. Other tabs and a running sync cannot change the data while the page is open (ADR-026, ADR-055), so nothing else refreshes it behind the user.
  - **Month headers:** worked out over all rows shown, so a month split between two batches has one header.
- **Rejected:** drawing only the first rows of an already read list (the first read stays slow), a virtual list (a new dependency and rows of different heights), offset paging (rows shift when something is added), a "Show more" button (the user chose automatic loading), and remembering how far the user had scrolled (a heavy redraw on return).
- **As built:** the page reads `max(30, rows shown)` through a ref set after each render; the hook resets its extra batches when the base object changes (so the base must be a stable object, as the cached query's data is); no watching while a batch loads or has failed, and watching again after each batch (the effect depends on the row count), so a list still short of the view keeps asking; where there is no `IntersectionObserver` nothing is watched.
- **Tests:** the service (the cursor across batches, a tie on date and creation time, exactly 30 rows giving no next, deleted and payment rows counting, a non-member), the hook and page with a stubbed `IntersectionObserver` (first 30 only, the next batch on reaching the end, no repeat, the spinner, the failure row and Try again, one month header across batches, reading again keeps the length), and that the balances still count every expense. Break-checked by 34 deliberate breaks (the cursor's columns and time, the extra row, each hook guard, the margin, each watching condition, the spinner, the failure row, and the length kept on reading again), all caught; two were redundant code and changed: a watching condition that the failure row already made true, and a hang-proofing of the paging helper in the tests.
- **Addendum (ADR-060): the rows are kept between visits.** "A page opened again starts at the first 30" was reversed: coming back, the page must show the row the user left, where they left it. `useExpenseBatches(base, readNext, cacheKey)` keeps its later batches (with the read they follow and the next cursor) in the query cache under `groupBatches` and the user and group, and starts from them on the next visit; when the page's own read comes back as a new object it starts the batches over as before (that read already holds as many rows). A change to the data forgets them with the page (ADR-051). Tests in `useExpenseBatches/__tests__`.

## ADR-059: Back arrows go back in the history instead of adding a page
- **Context:** the Back arrows (and Cancel, Save and Delete that return) did `navigate(group)`, which adds a page. From a group, Edit group, the header's Back, then the browser's Back, the user was shown Edit group again: the history held group, edit, group.
- **Decision:** `useAppNavigate` with `direction: 'back'` pops the history (`navigate(-1)`) when the page just before is the target. The app remembers the path of each history position it has been at (`slide.paths`, set by `PageTransitions` from the router's `history.state.idx`), and `previousPageIs(target)` compares the position before with the target's path (query and fragment ignored). When it is not the one before (a link from elsewhere, another way in), or after a reload (nothing remembered), the target replaces the page (`replace: true`), which also leaves the page behind out of the history. A `replace` with a direction still slides (the old rule skipped it). The slide of a pop is the browser-Back slide of ADR-057 (`installSlideOnBrowserBack`). Forward moves still add a page.
- **Rejected:** always `navigate(-1)` (a deep link or a reload would leave the app, or go somewhere other than the Back arrow's target), and always replacing (a duplicate of the target stays in the history: group, group).
- **Consequences:** the browser's Forward still shows the page left, as for any pop. Chrome keeps at most 50 history entries per tab, which made manual checks in a long-used tab misleading; test in a fresh tab. A reload loses `slide.paths`, so the first Back arrow after one replaces instead of popping.
- **Tests:** `useAppNavigate/__tests__/back.test.tsx` (jsdom's real history: popping, the browser's Back after it, replacing when the page before is another or unknown, forward and replace unchanged, the slide, and `previousPageIs`). Break-checked by 9 deliberate breaks.

## ADR-060: Pieces that travel between pages (shared-element transitions; built on branch `group-hero-transition`)
- **Context:** ADR-057 slides whole pages. The user wanted the home list's group row to morph into the group page's header (PRD 5.16), tried on a separate branch (`group-hero-transition`) so it could be dropped; it grew into five pairs of pages, reviewed on a phone one by one.
- **Decision:** the browser's View Transitions API with named pieces (the technique below), for these pairs (`groupHeroFor` in `src/hooks/useAppNavigate/hero.ts`): a group's row and its page, an expense's row and its page, the home page's Create group pill and Create group's page, a group page's Add expense and Settle up pills and their pages (all both ways), and Create group's chosen type tile into the new group's band (one way). Every other page change keeps ADR-057's slide. The morph lasts `GROUP_OPEN_MS` (600 ms); the rest of the screen slides (`GROUP_OPEN_REST` `slide`; `fade` is kept as a choice).
- **Rejected along the way:** a cross-fade of whole pages under the pieces (the first build, `fade`: the content ghosted), morphing the whole page container into the group page's (it stretched every piece of content), blending the list's green background into the group's (the green moved with the content; solved instead by keeping the background still, below), a date column growing into the expense's date chip (it ballooned; the chip comes in from the right), the group-name field growing into the band's title on Create group (a white box crossing a light page read as a glitch; the title comes in from the right), and squaring a tile's own corners just before the picture (they flashed square).
- **What else had to change for it (each one a rule now):**
  - **Arriving filled in:** the browser ends a transition as soon as a named piece leaves the page, so a page must not swap its loading view for its content while the pieces travel. The expense page holds its known band until the morph ends (`slide.morph`); Add expense and Settle up, like Edit group (ADR-055), have their data read while the group page is on screen, so they open with their form (`ADD_EXPENSE_PAGE`, `SETTLE_UP_PAGE` and their loaders in each page's `utils.ts`, read with `useCachedData` and `prefetchCachedData`); and a change made on a page that then goes to the group (saving a payment, an expense or the group's details, deleting an expense, creating a group) reads the group page first, with `refreshGroupPage` (`src/pages/group/utils.ts`, which also holds the page's own loader, `loadGroupPage`), since the change made the app forget it (ADR-051). Found on the phone: saving a payment showed the group's loader and cut the way back short after a fraction of a second.
  - **A new group replaces Create group** in the history (`replace` with `direction: 'forward'`, which `useAppNavigate` now slides and morphs: a replace without a direction still only fades), so the browser's Back from the new group goes to the list.
  - **Scroll positions** (ADR-057 addendum): going back returns to where the page was scrolled before the transition takes its picture, and the group page keeps the rows it had loaded (ADR-058 addendum), so the row a band shrinks into is on screen.
  - **Pills are a frame and a square button:** `FloatingPillButton` and the Settle up pill (`ActionPills`) are a rounded frame that clips (and casts the shadow or draws the outline) around a square button (`data-vt="block"`) holding the label (`pillLabel`); the frame drops its shadow or outline while its button travels (CSS on `:has(> [style*='view-transition-name'])`), else an empty pill would slide away with the page. The same square-block-in-a-frame shape is `CategoryIcon`'s and `GroupTypeIcon`'s `travels`.
  - **Messages stay in front:** Ant Design's message list sits outside `#root`, so it would be part of the still background picture, under the sliding pages; it has its own picture (`app-message`) above everything, shown at once, not faded in over the transition.
  - **Confirmations stay in front too:** a confirmation whose button changes the page (the "Discard …?" dialogs of Create group, Add and Edit expense, Settle up and Edit group, and "Delete this expense?") was part of the still background as well, so after Discard it vanished behind the pages at once. It opens in a container of our own, `dialogLayer()` (`src/components/DialogLayer`, given as the confirmation's `getContainer`): an element made on first use that then stays on the page, covers the screen (letting clicks through to the page; the dialog inside takes them) and has its own picture (`app-dialog`, under the message's) with no animation. The new page's picture is live, so the dialog closes there with Ant Design's own animation over the page change; the old page's picture, the dialog frozen as it was before the click, is hidden, or it would stay on screen until the change ends. Rejected on the way: naming the dialog's own wrapper (it is made when the dialog opens and removed once it has closed, so the browser cut the page change short after about 250 ms, and having no height of its own it gave an empty picture), and a fade of the frozen picture marked just before the change (the same cut-short page change). Found in slow motion in headless Chrome; the browser pane's screenshots lag behind during a transition, and the dialog's own opacity read from the page is not what the screen shows. Other dialogs and sheets (pickers, the members sheet, the sign-in prompt) do not change the page and keep Ant Design's default container.
  - **Wording follows the morph:** the home row reads "£ · 3 members" (currency first, as the band's symbol) and the band's chip "3 members" (it said "3 people"), so the texts that travel are the same.
- **Tests:** jsdom has no View Transitions, so the tests check the pairs and the names, not the motion: `useAppNavigate/__tests__/hero.test.ts` (each pair, its corners and kind, the names put on the right elements and taken off, only the tapped row and the chosen tile, chips as whole pills for a new group), `useAppNavigate/__tests__/index.test.tsx` (a replace going forward morphs, a replace going back only slides), `PageTransitions/__tests__/scroll.test.tsx`, `useExpenseBatches/__tests__` (rows kept between visits), `pages/__tests__/backToGroupFilled.test.tsx` (each save or delete, and a new group, arrive with no loader; a new group replaces Create group), `pages/__tests__/editOpensAtOnce.test.tsx` (Add expense and Settle up open at once), the tile and pill shapes in `GroupTypeIcon`, `GroupTypeSelector` and `FloatingPillButton` tests, and the confirmations: `DialogLayer/__tests__` (one marked element on the page, the same for every dialog, made again if taken off) and a check in each confirmation's page test that it opens in the layer. Break-checked by 30 deliberate breaks, all caught, then 10 more for the confirmations (each page opening its dialog elsewhere, a new layer each time, a removed layer reused, the mark and the placing on the page left out), all caught; one more was redundant code and was removed. The layer's CSS (its picture, the hidden frozen copy) is not reachable in jsdom and was checked in slow motion. How it looks is checked by hand in the browser pane, headless Chrome and on the owner's phone.
- **Technique, as built (follow it for a transition like this between other pages):**
  - **How the browser does it:** `startViewTransition` takes a picture of the old page and of the new one. Every element with a `view-transition-name` becomes a picture of its own, and the browser moves and resizes it from its old box to its new box while cross-fading the two pictures. Everything without a name is flattened into one picture, `root`, background included. Nothing inside a picture can move on its own, and a picture is a snapshot: what changes on the page while the transition runs shows only when it ends.
  - **Name pieces only while the transition runs:** a name must be unique on the page, so the pieces are marked in the markup (`data-vt="block"`, `"icon"`, `"name"`, …, the row by `data-group-row`, the band by `data-group-band`) and `hero.ts` turns the marks into names: `before()` on the page left, just before `startViewTransition` (the browser takes its picture of it), and `after()` on the page that comes, once it is committed and before the browser takes that picture (inside the transition's callback, in `slide.waiting`). Both return what takes the names off, called when the transition ends. One table (`GROUP_PIECE_NAMES`) maps marks to names.
  - **A piece with a counterpart morphs; one without needs its own animation:** a name on both pages morphs (block to band, icon, name, the chip texts). A name on one page only is an old-only or new-only picture that by default just fades; give it a keyframe to come or go some other way (`group-header` from the top, `group-from-right` from the right, `group-app-header` up off the screen).
  - **Make something grow from nothing:** to have an element appear to grow out of the row, put an empty 0 x 0 px element there with the same name (the row's `peopleIcon`, centered on the text's line with `vertical-align: top` and half the line as a top margin) and let it morph into the real one.
  - **Morph a text into a pill:** name the text and, separately, a plain box around it in the row and the pill around it on the band (`currencyChip`, `peopleChip`), so the box grows into the pill while the text travels on top.
  - **Stretch, don't keep proportions:** the browser draws each picture at its own aspect ratio (`block-size: auto`), so a square block would stay square inside a wide band. `inline-size: 100%; block-size: 100%; object-fit: fill` on the old and new pictures of a stretching piece (the band and the two pills) makes them fill the moving box.
  - **Rounded corners (take the picture square, round it with a clip):** a picture's corners are part of the picture, so when it is stretched they stretch with it (an expense tile's 12 px corners became wide curves inside the growing band). Instead the rounding is a clip: `overflow: clip` and an animated `border-radius` on the piece's `::view-transition-image-pair`, which holds both pictures and is the size of the moving box at every frame, so its corners never stretch (`group-band-straighten` from the row's radius to 0 when opening, `group-band-round` back). The starting radius is the row's, set as `--hero-block-radius` on `<html>` when the transition starts (`setGroupOpenStyle`, from the hero's `blockRadius`): a group card's `24px 0 0 24px` (only its left corners are round, since its card clips the block), an expense tile's `12px`. A block must therefore be square itself and look round only through a parent that clips it, because the browser takes a named piece's picture without its parents' clipping: a group's block is clipped by its card, and a travelling expense tile (`CategoryIcon` with `travels`) is a square colored block inside a frame with the radius and `overflow: hidden`. (Squaring the tile's own radius just before the picture was tried first: the square corners showed on screen for a moment after the click.) The image pair also holds the row's radius as a plain style, not only in the animation, since the browser shows the old picture before the animations start, while the new page is drawn.
  - **Keep a named element mounted until it arrives:** the browser ends a transition (it reports it finished, without an error) as soon as a named piece of the new page leaves the page. The expense page shows a loading view with the band on a first visit and replaces it with the full page, a different component and so a new band element, when the expense has been read, about 100 ms in, which ended the transition at once. `slide.morph` (`useAppNavigate/utils.ts`) is a promise that settles when a running morph ends, set by `useAppNavigate` and `useSlideOnBrowserBack`; the expense page keeps its loading view until it settles. A page whose band is the same element in both states (the group page: `GroupBand` at the same place in the tree) needs nothing.
  - **More pairs:** `groupHeroFor` also pairs the group page with an expense's page: the expense row's category tile (`CategoryIcon` with `travels`), or a payment's arrows icon, grows into the band, the description and the amount (`group-amount`) travel, the band's header comes from the top and its day and category chips from the right (`chips` marks them, sharing `group-from-right`), the group's band goes up (named `group-app-header`, like the list's header bar) and the floating buttons drop and rise. A deleted line has no `data-expense-row` and a deleted expense's band no `data-expense-band` (`ExpenseBand`'s `travels`), so they keep the plain slide; `groupHeroFor` returns null when the row (opening) or the band (going back) is not on the page. Going back, the group page returns with every row it had loaded and where it was scrolled, so the row is on the page.
  - **Keep the background still while the content slides (the hard part):** the `root` picture holds the page's background, so sliding it slides the background too. Instead, name the app's whole content (`#root > *`) as well: on the page left `group-page-old`, on the page that comes `group-page-new` (it is the same element on both pages, so it needs a different name for each, set in `before()` and `after()`), and slide those two pictures, which have no background. `root` then holds only the plain page background and stays still (its animation is a cross-fade of two identical colors). A colored wash that should change in place (the list's green, the fixed `data-page-tint` layer of `TintedPageBackground`) gets its own name (`group-tint`) and simply fades out (or in, going back) over the still background.
  - **More pairs, the pills and the form:** a pill (`kind: 'pill'`) grows into a whole page: its square button is named `group-band` like a block, and on the page that comes the fixed wash (`data-page-tint`) carries that name, so the pill grows into the page's background, over the old page and under the new page's content (its own layering, `data-hero-kind='pill'`); its radius is half its height. Create group's chosen tile (`kind: 'form'`) grows into the new group's band like a row's block, and the band's title and chips, which the form has nothing like, come in from the right (`data-hero-kind='form'`). `nameChildren` takes the pieces to leave out, so a chip travels as one pill there.
  - **Layer the pictures explicitly:** named pictures are stacked in paint order, so a wash or a page named inside the content would cover it. `z-index` on the `::view-transition-group` of each sets the order: background (`root`, -4), wash (-3), the page underneath (-2), the page on top (-1: the one that comes when opening, the one left when closing), and the morphing pieces on top (auto).
  - **Direction:** `useAppNavigate` and `useSlideOnBrowserBack` ask `groupHeroFor(from, to)` and, for a pair it knows, set `data-nav` on `<html>` to `hero-open` or `hero-close` (and `--group-open-ms` and `data-group-rest`), which every CSS rule of this transition is keyed by, so the ordinary slide (ADR-057) is untouched.
  - **Checking it:** in the browser pane (when its page reports `visibilityState` `visible`; a hidden page runs no view transition) or headless Chrome, with a style that sets `animation-duration: 9s !important` on all four pseudo-elements for slow motion, screenshots at fixed times, and `document.getAnimations()` to list which pseudo-element runs which keyframe.
  - **Known issue:** a page change started while another is still running is cut short, and the first one's cleanup deletes `data-nav` set by the second, which then plays the plain slide. Seen only in slow motion; not fixed yet.

## ADR-061: Accounts and the payment method of an expense
- **Status:** built (October 2026, branch `accounts`). Behavior and copy are in PRD 4.10, 5.5, 5.6, 5.6a and 5.17; "As built" at the end of this entry lists what changed from the first decision.
- **Context:** the user wants to record which bank account or credit card paid an expense, to set a spend target on a card, and to handle a forex card, where an expense in dollars is debited from an INR account in a different amount.
- **Decision:**
  - **Private by design:** accounts and the payment method of an expense belong to the user alone. They are in the backup (ADR-044) and never in a group file, so no other member learns an account's name or which account paid. Rejected: sharing them with the group (exposes card names to every member).
  - **Schema (migration 0012, approved with this ADR):** two new tables, both with the usual sync columns (`updated_at`, `updated_by`, `deleted_at`, ADR-025) so the backup's newest-wins merge works.
    - `accounts`: `id`, `kind` (`bank` or `card`, check constraint), `name` (1 to 60), `currency` (ISO code, as `groups.default_currency`), and, for a card only, `statement_day` (integer 1 to 28, nullable), `credit_limit_minor` (bigint, nullable), `spend_target_minor` (bigint, nullable) and `spend_target_period` (`month` or `quarter`, nullable). A check constraint keeps the last two both set or both null, and the card-only columns null for a bank account. Money is integer minor units with the account's currency (CLAUDE.md). There is no owner column: a device has one Google account (ADR-035), so every account on it is the user's, and the backup merge joins devices of the same account by id. No delete exists yet, so `deleted_at` stays null (kept for the rule and for later).
    - `expense_payments`: `id`, `expense_id` (unique: one payment method per expense), `account_id`, `charged_minor` (bigint, nullable: what the account was debited, in the account's currency), and the sync columns. Clearing a payment method sets `deleted_at` (never a hard delete); choosing one again clears it. It sits in a table of its own, not as a column on `expenses`, because the expense row, its events and its snapshots are shared with the group (ADR-010, ADR-042): a column would travel in the group files and in every version, and would have to be stripped at each place, while a table that group files never read cannot leak.
  - **Not in the history:** changing the payment method writes no `expense_events` row and does not change `expenses.updated_at`, so it is not activity (ADR-028) and a version (ADR-043) never restores it. Rejected: putting it in `ExpenseSnapshot` (shared and versioned).
  - **Two currencies:** an account has one currency, the one it is debited in. The expense keeps its own amount and currency, so splits and balances do not change (ADR-012, no conversion). `charged_minor` is the extra optional amount, entered when the account's currency differs from the expense's, because the bank's markup and fees make the real debit differ from any rate the app could look up. The rate is derived for display: `(charged / 10^accountDecimals) / (amount / 10^expenseDecimals)`, shown with 2 decimals, or 4 when below 1. It is never stored. Rejected: storing an exchange rate (not what the statement says, and an offline app has no rates), converting the expense (breaks ADR-012), and one multi-currency account with a balance per currency (a wallet model with its own rules; for now one account per currency).
  - **Spend:** `accountService.spend(db, userId, accountId, period)` sums, over live `expense_payments` of the account whose expense is live, the user's `paid_minor` on that expense, replaced by `charged_minor` when set; when `charged_minor` is null and the expense's currency is not the account's, the expense is not counted and is returned in a `skipped` count (shown on the card). The expense's `date` decides its period. Periods are pure functions (`utils.ts`, unit-tested): a month starts on the statement day (day 1 when there is none) and ends the day before the next; a quarter starts on that day of January, April, July or October, whichever is the latest not after today, and ends the day before three months later. The statement day stops at 28 so every month has it. `paid_minor` is used so that several payers (a future feature) would each count only what they paid.
  - **Limit:** the card shows its limit and the spend of the current statement cycle as a share of it. It is not the balance owed or the credit left, since repayments are not recorded; the page's copy says "spent this statement cycle".
  - **Service and pages:** `src/services/accountService` (`listAccounts` with the current spend, `createAccount`, `updateAccount`, `setPaymentMethod`, `getPaymentMethod`, and the period helpers), validating with zod in `schemas.ts`, returning field errors (ADR-027); names are unique among the user's accounts (ignoring case and spaces) as a convenience check on this device. `updateAccount` refuses a currency change once any live expense payment uses the account. The page is `src/pages/accounts` at `ROUTES.accounts` (`/accounts`), with its card and dialog under `components/`, opened from an "Accounts" item below "Group members" in the avatar menu. `expenseService.createExpense` and `updateExpense` stay as they are for the shared expense; the form's payment method is saved by `accountService.setPaymentMethod` after, in the same database transaction where possible, from the add and edit pages. `getExpense` returns the payment method of this device for the details page only (never in a group export). A new `PaymentMethodField` (`src/components/ExpenseForm`) holds the row, the picker and the "Charged to the account" field.
  - **Backup and sync:** both tables are added to `exportAll`, the backup file's zod schema and the merge (accounts before payments, payments after expenses, newest `updated_at` per row; `expense_payments` also by `expense_id`), and are left out of `exportGroup` and group-file merging. `completeness.test.ts` must be taught that these two tables are in the backup but not in a group file (a short list beside `NOT_BACKED_UP`, with the reason), and needs test data for every column of both. `userService.mergePeople` re-points `updated_by` on both tables. A change announces itself through `notifyAfter` (ADR-051), and the new service gets a `logActions` entry and log tests (ADR-048): ids, counts and statuses only, never names, amounts or currencies' values.
- **Rejected:** a payment method on settle-up payments (payments between members are not the user's own spending, and the PRD leaves it for later), a free-text payment method (no spend, no forex), an account per group, and showing the user's account name to the payer's group.
- **Consequences:** a schema change. An expense that another member paid has no payment method on this device, and the same expense has none on another device of the user until the backup merge brings it in (a full Sync). The names of accounts appear on screen only for the user. Deleting or archiving accounts is left open (PRD), so `deleted_at` on `accounts` is unused for now.
- **Tests to write when it is built (break-checked, CLAUDE.md):** period maths (statement day, month and quarter edges, year change, the 28th), the spend sum (charged amount, same currency, skipped, deleted expense, other payer), validation and messages (unique names, target needs period), the currency lock, the service against in-memory PGlite, the backup round trip and completeness, a group file that holds neither table, the pages (list, dialog, menu entry, cards) and the form (row shown only to the payer, cleared when the payer changes, charged field only for another currency, rate line, edit with only the payment method changed writes no event), and the logs.
- **As built (what differs from, or adds to, the decision above):**
  - **Where:** `src/services/accountService` (`createAccount`, `updateAccount`, `listAccounts` with each card's spend, `setPaymentMethod`, `getPaymentMethod`, `rateLine`; `listOptions` was dropped: the expense form reads `listAccounts` too, so the picker's cards can show a card's spend), `src/pages/accounts`, and shared components in `src/components`: `AccountKindIcon`, `AccountHeading` (icon, name, "£ · Bank account"), `AccountStats` (the spend target and credit limit tiles, each with a ring), `AccountDialog` (opened by the accounts page and by the payment method picker), and `ExpenseForm/PaymentMethodField`. Migration 0012 is `0012_accounts.sql`.
  - **Bank accounts ignore card options:** `accountSchema` drops a card's options (statement day, limit, target) from the input of a bank account before it checks anything. The dialog keeps what was typed for a card after the user switches to Bank, and a typed-then-hidden value that fails a card rule (a limit of 0) must not block saving a bank account (found by a test).
  - **The row is always there for the payer:** the Payment method row is shown even with no account (the picker then offers None and Add account), not only once the user has one.
  - **History:** changing the payment method adds no History entry (decided with the owner, who first asked for one and then cancelled it): the History is shared with the group, and a private entry would have needed a private table of its own.
  - **Rate both ways:** `rateLine` writes it in both directions ("US$1 ≈ £0.7850 · £1 ≈ US$1.27") with em spaces around the dot (an ordinary space collapses on a page); it replaces the one-way `rate`.
  - **A shared look:** cards (20 px radius, 10 px padding, a button's border), the grey sheets and the round Add buttons are theme and CSS rules, not per-page styles: `themeFor(scheme)` in `src/components/ThemeProvider/utils.ts` holds the theme (extracted so tests can read it), `src/index.css` the rest. The card radius is a third value next to inner (now 10) and outer (24); CLAUDE.md says so.
  - **Folded card fields:** the card-only fields of the dialog stay mounted and fold shut with a grid-rows transition (`.account-card-fields`), `inert` while shut, so the sheet's height changes smoothly (no jump from switching `tall`); bottom sheets are capped at 85% of the screen with a scrolling body (`.ant-drawer-bottom .ant-drawer-section`).
  - **Tests:** `accountService/__tests__` (period maths, validation, update and currency lock, spend, payment method, rate line, logging, announcing), `backupService/__tests__/accounts.test.ts` and the completeness test (both tables in the backup, empty in a group file; `PRIVATE_TABLES`), `mergePeople`, the accounts page and dialog (`pages/accounts/__tests__`), the payment method on add, edit and details pages (`paymentMethod.test.tsx` in each), `AccountStats`, `AccountHeading`, `AccountKindIcon`, the theme, and the menu entries. Break-checked by 70 deliberate breaks, all caught; two checks were redundant code and were removed (a payer check in `paymentMethodOf`, a fixed progress status), one more was caught by a new test (a payment method kept for an expense someone else now pays).
  - **Not built (still open in the PRD):** deleting or archiving an account, card repayments, multi-currency wallets, a payment method on settle-up payments, several payers.

## ADR-062: The Activity page
- **Status:** built (October 2026, branch `activity`). Behavior and copy are in PRD 5.18.
- **Context:** every expense event is already recorded in `expense_events` (ADR-042) with a snapshot, a group id and who acted, and ADR-042 named an Activity page as the reason. The user wants one feed across groups with a marker for what is new.
- **Decision:**
  - **Reading:** `activityService.listActivity(db, userId, { limit, after })` returns `{ items, next }`, keyset-paged like `listExpensesPage` (ADR-058) over `expense_events` joined to live groups where the user has a live membership, ordered by `occurred_at`, `id` descending. The cursor keeps `occurred_at` as the database's text (a JavaScript date would round it, ADR-058). Each item has the event's id, kind, actor (`isYou`, name), time, the group (id, name), and from the snapshot the description, category, amount, currency and whether it is a payment (with the people for the sentence), so a row needs no second read. `ACTIVITY_PAGE_SIZE` is 30. A user who is not a member of an event's group sees nothing of it. The service takes `db` first, validates input with zod, and gets a `logActions` entry (ADR-048).
  - **Edit lines:** each item carries the event's `changes`, `currencyBefore` and `restoredFromAt`, and the page names the people they refer to (as `getExpense` does, `peopleReferredBy`), so a row shows the History's own lines (`historyLines`, nested split lines included) without a second read.
  - **Unread by arrival (schema change, approved with this ADR; migration 0013):** the event's own time says when something happened, not when this device learned of it, so a sync that brings in old events could not mark them new. A local table `event_arrivals` (`event_id` primary key referencing `expense_events.id`, `arrived_at` timestamptz) records, for events by other members, when they reached the device. It is local-only: not in the backup or group files, listed in `NOT_BACKED_UP` with its reason, with test data in the completeness test (ADR-044). It has none of the sync columns, like `sync_status`. Written by `importGroup` (a member's file, and a group found for the first time) for each event it inserts; not by `importAll` (the user's own backup, so a cleared device does not light the dot), and not by the user's own actions (their events never count). The migration backfills one row per existing event whose `acted_by` is not the user's person, with `arrived_at` the migration time (decided: they show as new once). The user's person is not known to SQL, so the backfill marks every event and `unreadState` ignores the user's own by `acted_by`. Merging two people (`mergePeople`, ADR-035) re-points nothing here.
  - **Unread:** `activityService.unreadState(db, userId)` returns the time last seen and whether any arrival after it belongs to an event by another member in a group the user is in; `markSeen(db, userId)` writes now. The time is a row of `sync_status` with the scope `activity-seen` (ADR-044), so it goes with the data when that is cleared. A first visit has no row, so everything that has arrived is new.
  - **After a sync:** `importGroup` reports how many arrival rows it wrote (events by others); `useSync` adds them over the run and, when the total is above 0, adds a line with an Open Activity link to the dialog and, on close, shows an Ant Design message for 6 seconds with an Open button (the dialog is a blocking sync, ADR-055, so the toast belongs to the close). Opening Activity from the dialog cancels the message. Counts go in the log (ADR-048), never names.
  - **Version page:** its Back arrow uses `useAppNavigate` with `direction: 'back'` to the previous page when it is Activity (ADR-059 pops the history when that page is the one before), else the expense as now; it gains an Open expense `AppLink`. This changes its `backTo` from fixed to "where it came from", passed in router state by the Activity row (`from: 'activity'`) and ignored for any other value.
  - **Row:** `PersonAvatar` as a 20 px badge over the 40 px `CategoryIcon`, for every actor including the user.
  - **When it is marked seen:** on leaving the page (the page's unmount), not on opening, so the highlights stay while the page is read. The page computes which rows are new from the `seen` time it read when it opened and keeps that for the visit. `markSeen` announces a change (ADR-051) so the menu dot refreshes.
  - **The dot:** the avatar menu (`AppHeader`) reads `unreadState` through `useCachedData` and shows a dot on the avatar and on the "Activity" entry. It refreshes after a finished sync (which already announces, ADR-051) and after `markSeen`.
  - **Page:** `src/pages/activity` at `ROUTES.activity` (`/activity`), built like the group page's list: a hook for the batches that survive leaving and coming back (ADR-058 addendum), a row component per event, the shared `LoadingMessage`, `LoadError` and `CenteredMessage`. Rows link to `ROUTES.expenseVersion` with the event's id.
  - **Wording:** the row's sentence is a pure function beside the page, built from the History's words (`historyHeader`, ADR-043), unit-tested; the lines under an edit are the shared `historyLines`.
- **Rejected:** group events now (they are not recorded; recording them is its own schema and service change), marking seen on opening (the highlights would vanish at once), `localStorage` for the seen time (separate from the data, shared by the whole origin, ADR-032), showing only other members' events (the user chose the full feed), a bottom tab bar (touches every page, ADR-030), and a per-device unread count per group (not asked).
- **Rejected, unread:** comparing the event's own time with the last-seen time (a sync of old events would never light the dot, the user's choice), and an `arrived_at` column on `expense_events` (the table is exported and merged, so the column would have to be stripped from exports and kept on merge, as `local_name` is, ADR-045).
- **Consequences:** a schema change (the approved table above). Events that arrive by sync (ADR-044) show as new for other members' actions once merged, and a deletion and a restoration are separate rows. The first visit after the update shows every existing event by others as new (decided). The feed's rows are taller for big edits. The feed grows with the history; paging keeps each read small. Unread is per device: the same account on two devices tracks it separately.
- **As built (what differs from, or adds to, the decision above):**

## ADR-063: The browser's Back button closes overlays
- **Status:** built (October 2026, branch `back-closes-overlays`). Behavior is in PRD 5.19.
- **Context:** Back (and a phone's Back gesture) left the page while a sheet or dialog was open, which people expect to close the sheet. The app's history rules (ADR-057 slides by the router's history position, ADR-059 pops or replaces for its Back arrows) assume one history entry per page.
- **Decision:**
  - **One entry per open overlay:** when an overlay opens, a shared hook (`useCloseOnBack`, `src/hooks/useCloseOnBack`) pushes a history entry marked with the overlay's id (`history.pushState` with a marker in `history.state`, the router's own `idx` and `key` kept so the router is not confused), and when the overlay closes by any other means it goes back one step to remove it. A `popstate` that removes the top overlay's entry closes that overlay (`onClose`), and only that one: each overlay keeps its own entry, so stacked ones close in turn. Used by `AdaptiveDialog`, the members sheet and the confirmations (`modal.confirm` is opened through the same hook).
  - **Not dismissible, no effect:** an overlay with `dismissible` false (the sync dialog during a run) does not close on Back: the hook puts its entry back (`go(1)` / `pushState` again) so the user stays on the page, and the entry is removed once the overlay closes.
  - **No page slide:** the pop of an overlay's entry is recognized by its marker and is not passed to the slide handler (`installSlideOnBrowserBack`, ADR-057), which otherwise holds back and replays a `popstate`; `slide.index` and `slide.paths` (ADR-059) are not advanced for an overlay's entry, so `previousPageIs` still compares real pages.
  - **Close and go:** a page change made while overlays are open (`useAppNavigate`) must end with the same history as without them (ADR-059). The overlays' entries are removed first (the hook's cleanup, a `history.go(-n)` that waits for its `popstate`), then the navigation runs; `previousPageIs` and the pop-or-replace choice then see the real pages. This sequence is the risky part and is settled in the build, checked in the browser, with a test for each case (Discard, Delete, Open Activity from the sync dialog, a Save that returns).
  - **Reload:** at start (`main.tsx`, with `restoreRedirectedUrl`, ADR-032) an entry that carries an overlay marker is replaced by the page's plain state, so Back from a reloaded page goes to the previous page in one press.
  - **Forward:** a `popstate` onto an overlay marker that has no open overlay changes nothing (the hook ignores unknown markers) and the page stays.
- **Rejected:** intercepting Back with `beforeunload`-style prompts (not a close), React Router's data-router `useBlocker` (the app does not use the data router, ADR-027), a hash fragment per overlay (`#sheet`, which would change addresses and share links), reopening an overlay on Forward (each overlay would have to keep its state), and one entry for all overlays (one Back would close them all, which the user did not want).
- **Consequences:** an overlay opened by a program (no user step) still adds an entry. The history gains and loses entries as overlays open and close, and the slide, scroll and pop logic (ADR-057, ADR-059, ADR-060) must be checked in the browser and on a phone, since the browser's own navigation limit (about 50 entries per tab) counts them too.
- **As built (what differs from, or adds to, the decision above):**
  - **Where:** `src/hooks/useCloseOnBack/overlays.ts` is the manager (the stack of open overlays, `openOverlay`, `releaseOverlay`, `dropAll`, `handleOverlayPop`, `cleanUpAfterReload`), `useCloseOnBack` the hook that `AdaptiveDialog` and the members sheet call, and `src/hooks/useConfirm` replaces the six `modal.confirm` calls (Back is its Cancel: `onCancel`, then `destroy`; its step is released in `afterClose`).
  - **Recognizing an overlay's move:** an overlay's step copies the page entry's router `key` and `idx` and adds `overlay: <number open>` to `history.state`; `PageTransitions` keeps the key of the page on screen in `slide.key`. `handleOverlayPop` takes a `popstate` only when its entry has the same key as the page on screen **and** an overlay is part of the move (the step has a marker, the step the app was on before had one, or an overlay is open). So a `#fragment` move and a real page change go on to the slide handler and the router as before, and the step that an overlay's removal lands on is held back too. (First built with the key alone, which swallowed a `#fragment` move; found by the existing slide handler test.)
  - **Strict mode:** a step released in a tick is removed only when the tick ends (`removeUnclaimed`, a zero-length timer), and an overlay that opens meanwhile takes it over, so React's development remount neither adds nor removes a step.
  - **Close and go:** `useAppNavigate` always runs its navigation through `dropAll`, which removes the open overlays' steps with one `history.go(-n)` and runs the navigation when that `popstate` arrives (a 150 ms timer, `DROP_TIMEOUT_MS`, lets go if the history never answers), or at once when no overlay is open. The page change therefore ends with the same history as without overlays; Discard, Delete and Open Activity from the sync dialog were checked in the browser. (A first version tested `openOverlayCount()` before calling `dropAll`; break-checking showed `dropAll` already does that, so the test was removed.)
  - **Reload:** `cleanUpAfterReload` in `main.tsx`, before the router exists, walks back `history.state.overlay` steps with `go(-n)`; the `popstate` it causes is held back by the same rule (the step it leaves had a marker).
  - **Not tested:** the call to `cleanUpAfterReload` in `main.tsx` (wiring, checked by reloading with a sheet open in the browser pane) and the phone's Back gesture, which sends the same `popstate`.
  - **Tests:** `useCloseOnBack/__tests__` (the manager against jsdom's real history and the hook), `useConfirm/__tests__`, `useAppNavigate/__tests__/overlays.test.tsx` (close and go, including going back and a history that never answers), `useSlideOnBrowserBack/__tests__` (no slide, fade or page change for an overlay's step), `PageTransitions/__tests__`, `AdaptiveDialog/__tests__` (phone and wide screen, a dialog that must stay), `SyncDialog/__tests__` (during and after a run), `pages/group/__tests__/backCloses.test.tsx` (the members sheet, stacked sheets). jsdom's `popstate` is held back from later listeners by the manager, so the tests wait on a short timer rather than for the event. Break-checked by 34 deliberate breaks, all caught.

## ADR-026: Opening the database, migrations and tab lock
- **Decision:** the database is opened for one account at a time as `idb://ownledger-<google account id>` through `src/db/client.ts` (`openDatabase`, `getDb`, `closeDatabase`). ## ADR-027: Form validation
- **Decision:** forms use Ant Design `Form` for the screen and zod for the rules. The rules of a form are written once, as a zod schema (for create-group: name 1 to 60 characters, `@gmail.com` member emails lower-cased and unique, a valid ISO currency, one of the four types). The Ant Design form has no field rules of its own: on submit it passes its values to the save function, which validates them with the schema and returns one message per field, and the form shows them with `form.setFields`. Format problems and functional ones (such as a taken name) therefore come back the same way, and the rules exist in one place with no adapter. A message is cleared when its field is edited. Checks run only when the user presses the submit button, as chosen for create-group. The database constraints remain the last safety net.
- **Functional checks** (those that depend on existing data, such as "a group with this name already exists") run inside the save function, in the same transaction as the insert. They return field errors, which the form places beside the right field, rather than throwing. Unexpected failures (the database not open, a query error) throw and show a general error message.
- **Limits:** a duplicate group name can only be detected on this device. Groups created by other members on other devices meet only at sync time, so such checks are a convenience, not a guarantee.
- **Leaving a form with unsaved input:** the page's own Back and Cancel buttons ask for confirmation, and a `beforeunload` handler covers reload and closing the tab. The browser's Back button is not intercepted, because `useBlocker` only works with React Router's data router (`createBrowserRouter`) and the app uses `BrowserRouter`. Switching routers is a possible later change.
- **Rejected:** react-hook-form or Formik (duplicate what Ant Design `Form` does), and keeping the rules only inside the form (they could not be reused by the save function or tested on their own).

## ADR-028: Signed-in layout and the group list
- **Decision:** signed-in pages share one layout route (`SignedInLayout`) that opens the user's data and shows the header (the OwnLedger name and an avatar menu with the user's name, email and Sign out) on the home page only. The other pages have Back buttons and start at the top of the screen (padding from `belowStatusBar` in `src/theme/safeArea.ts` keeps them clear of a notch or status bar). While the data is loading, locked or failed to open, `DatabaseGate` shows the header above those screens on every page (its `header` prop), so Sign out stays within reach; once the data is ready the layout decides by route (`useMatch(ROUTES.home)`). A page that is not home therefore briefly shows the header while the data opens on a fresh load. The layout is a column at least as high as the screen (`min-height: 100dvh`), so a page can fill what is left below its header with `flex: 1`. The home page and the group page use that for their empty messages: a box fills the space from what is above it (the heading, or the actions under the band) down to the floating button, and ends `ABOVE_FLOATING_BUTTON` (88 px: the button's 24 px offset, its 48 px height and a 16 px gap) above the bottom of the screen, and the message is centered in the box. Several simpler ways looked off and were dropped: a box running down to the bottom of the screen (the floating button takes the bottom of it, so the message sat too low, with more space above it than below, and the gap between the actions and the list made that 16 px worse); centering on the whole screen (fine under home's small heading, but too high under the group page's tall band). The space between the actions and the list belongs to the list (its `marginTop`), so an empty box starts right under the actions. A page column that is centered with `margin: 0 auto` needs `width: 100%` as well, since an auto margin shrinks a flex item to its content. Groups are listed by their latest activity, newest first: the later of the group's own `updated_at` and the newest `updated_at` of its expenses (deleted ones included, since deleting is a change), computed in the list query. A user's groups are those where they have a live (not deleted) membership, in a live group. A group page for an id the user does not belong to shows "Group not found", the same as for an unknown id, so the page does not reveal whether a group exists.
- **Loading data (changed by ADR-051: pages now remember what they read):** the home page and the group page read the database once when they open (the group page again after a member is added, ADR-038), through a small hook that exposes loading, error and retry states, rather than live queries. Live queries (the installed `@electric-sql/pglite-react`) would need PGlite opened with its live extension; they can be introduced later if a page must update while it is open, for example when sync brings in a new group.
- **Tab titles:** React 19 moves a `<title>` element into the document head, with no library, and restores the page's earlier title when the page goes away. The element must contain a single string: `<title>{name} · OwnLedger</title>` is two children and is silently ignored, so build the text first (`{`${name} · OwnLedger`}`).
- **Balances:** each row ends with the user's balance in the group, per currency (`expenseService.balancesByGroup`, see ADR-031); the home page loads it together with the list.
- **The logo and name are not a link (decided October 2026):** the OwnLedger logo and name in the header used to lead to the home page; they are plain content now, since pressing them did something the user did not expect. `AppLink` stays for the Back-style links elsewhere. Home is reached through the Back buttons.
- **Consequences:** `updated_at` must be set whenever a group or its members change, since it drives the order.

## ADR-029: Testing functional requirements
- **Decision:** each functional requirement in the PRD is covered by an automated test at the lowest level that can show it: pure rules as unit tests; data functions against in-memory PGlite with the real migrations; pages and forms as component tests that use `@testing-library/user-event` to type and click and `@testing-library/jest-dom` to check what is on screen. Component tests run in jsdom with a real in-memory database behind `getDb()`, not mocked queries, so a test fails if the page, the service or the schema disagree. A shared setup file adds the browser features jsdom lacks and Ant Design needs (such as `matchMedia` and `ResizeObserver`).
- **Testing Ant Design controls in jsdom** (learned while testing create-group): `setup.ts` also silences jsdom's pseudo-element warning; `renderPage` turns animations off so closed dialogs and cleared messages leave the screen at once. user-event's `{Enter}` is not understood by Ant Design's Select, so tests send raw `keyDown` and `keyUp` events with the Enter key code (the Select locks Enter until the key is released, so the key-up is required). Several addresses are added by pasting them or typing a comma, which are real features. The `option` roles of an open dropdown are a hidden screen-reader copy that shows only values; tests read the visible entries (`.ant-select-item-option-content`). A tag's x is hidden from screen readers and is found by class. Check state after each step of a sequence, not only at the end, or a change and its undoing can cancel out and hide a bug. Ant Design adds an icon's name in front of a button's own text ("team 2 people"), so tests match a button by the end of its name. A `Drawer` opens in a dialog named by its title; whether it slides from the bottom or the right depends on `matchMedia`, which a test replaces to pretend the screen is wide. A disabled button gets no pointer events, so the "Coming soon" tip is tested by hovering its wrapper.
- **Scope so far:** the create-group page, the C3 pages (header, home, group page), the add-expense page, the expense details page and the edit-expense page (`src/pages/editExpense/__tests__`: `form`, `states` and `photos`, sharing `helpers.tsx`). Two things learned there: a message such as "Expense updated." appears a moment before the router has moved, so a test waits for the path (`waitFor`) instead of reading it at once; and a form value that no Ant Design `Form.Item` is registered for is left out of what `onFinish` receives, so `keptReceipts` (the photos an expense already has) has a hidden item of its own. The welcome page keeps its current tests; extending component tests to it is possible later.
- **Limits:** jsdom has no layout, so responsive behavior and visual details (colors, spacing, phone layout) are still checked by hand in the browser. Real IndexedDB storage and the browser-only tab lock are not exercised by these tests either.
- **Learned while testing receipts:** IndexedDB comes from `fake-indexeddb` (import `fake-indexeddb/auto` in the test file). jsdom has no blob addresses, so `setup.ts` gives `URL.createObjectURL` unique fake ones; it cannot decode pictures either, so thumbnails drawn on a canvas, and how the chooser looks (the page's CSS once overrode its `hidden` attribute and showed it), are checked in the browser only. user-event's `upload` honours `accept`; a test that needs a non-picture to get through sets `applyAccept: false`.
- **Learned while testing add-expense:** Vitest's default 5-second limit per test was too short for long page flows when every file runs at once (a cold full run failed at random), so `testTimeout` is 20 seconds. Pages that show "today" fake only the clock (`vi.useFakeTimers({ toFake: ['Date'] })`), so user-event's timers still run. user-event and jsdom put the caret back themselves after a field is reformatted, so caret tests set the value with the browser's own setter, place the caret and send an `input` event (`typeAsBrowser`). Ant Design's Select lists only about ten options at a time (virtual list), so tests pick options near the top.
- **Speed and flakiness** (a full run used to take 60 to 90 s and failed at random when the machine was busy; it now takes about 30 s and held up under a run with every core busy):
  - *Why it failed:* every page test file starts its own in-memory PGlite in `beforeAll`, which took longer than Vitest's 10 s hook limit when about eight files started at once, so a whole file failed without running a test (the tests still counted as skipped). `hookTimeout` is now 60 s, and Testing Library's `findBy` and `waitFor` wait up to 5 s instead of 1 s (`setup.ts`), which only costs time when a screen is wrong.
  - *Workers:* Vitest starts about one worker per core, which is more busy workers than fast cores on a laptop (an M1 has 4 fast and 4 slow). Measured: 4 workers about 35 s, the default 7 about 65 s, and total CPU time dropped from about 290 s to about 130 s. `vitest.config.ts` uses threads and half the cores (at least 2).
  - *Styles:* Ant Design injects its CSS at runtime, and `getByRole` asks jsdom for the computed style of many elements, each time against thousands of rules. `renderPage` sets `zeroRuntime: true` on the theme, so no styles are injected; page tests ran about 35 % faster. The consequence is that a test must not depend on styles. Two did: button names such as "team 2 people" only had their space because the icon's CSS made it `inline-flex`, so `named()` now matches the end of the name without needing the space (and not as the end of a longer number), and a closed Ant Design drawer is only hidden by CSS, so the members-sheet tests check its `ant-drawer-content-wrapper-hidden` class. Anything that truly needs styles (colors, layout) is still checked in the browser (see Limits).
  - *File size:* the add-expense tests (62 tests, one file of about 37 s) are split into `fields`, `split` and `saving` test files that share `__tests__/helpers.tsx` (`setUpAddExpenseTests()` gives the in-memory database, `createGroup` and `renderForm`). Each test file still needs its own `vi.mock` of `getDb` (it is hoisted, so it cannot live in a helper).
  - *A stall that could not be reproduced:* twice a run sat for 5 to 10 minutes, one thread of the Vitest process at about 75 % of a core and no output, while a normal run takes 30 seconds. Ten clean runs in a row followed, so the trigger is unknown. A thread stuck in a loop cannot be stopped by Vitest's own timeouts (they need the event loop), so `bun run test` runs through `scripts/run-tests.mjs`: past 5 minutes (`TEST_TIMEOUT_MS` changes it) it takes a 3-second stack sample of the process (macOS `sample`, written to the temporary folder and named in the message), kills the whole process group and exits with 1. If it happens again, that sample says where the thread was stuck. Waiting for a stuck run to end by hand is never needed.
  - *Tried and rejected:* `userEvent.setup({ delay: null })` made no difference to speed and broke three tests that rely on the pause between actions. PGlite's startup (about 1 s per file) is left alone: sharing it between files is not possible, since each file runs in its own worker.
- **Libraries (dev):** `fake-indexeddb` (an IndexedDB for tests of the photo store), `@testing-library/user-event`, `@testing-library/jest-dom`, alongside `@testing-library/react` and `jsdom`.

## ADR-030: Group page design language
- **Decision:** the group page, and the app's phone-first look in general, follows the layout and interaction patterns of an existing expense-splitting app the project owner uses and wants a web version of: a colored header band with round action buttons and pill chips, a balance sentence, a row of action pills, an expense list with a date column, colored category tiles and a green or orange-red status on the right, and a floating "Add expense" button. We use our own colors (the band takes the group type's color), our own icons (Ant Design) and our own name; we copy none of that app's logo, illustrations or category artwork.
- **Message screens:** every full-page message (not found, couldn't load, open in another tab, couldn't open your data, opening your data) sits in `CenteredMessage` (`src/components/CenteredMessage`): a box that fills what the page's column has left, centers its content both ways and keeps to the 720 px column. On a page without a header that is the whole screen; on one with a header, the space below it; on the home page, which has a floating button, `roomBelow` ends the box above the button (the same 88 px as the empty message). The page must be a column that fills the screen, which `SignedInLayout` is. A page that shows a form or details next to such a message (add expense, expense details) renders the message instead of its column, not inside it.
- **Floating main action:** a page's main action is a floating green pill at the bottom right (`src/components/FloatingPillButton`): "Add expense" on the group page and "Create group" on the home page, which has no other Create group button (the one beside the heading and the one in the empty state were removed). The pill is shown in every state of the page, since the action does not depend on the list loading, and the page leaves about 112 px below its content.

A tip on a switched-off Ant Design button needs a wrapper element, because a disabled button does not receive pointer events.
- **Members:** the member list moved off the page into a sheet opened from the "N people" chip (bottom sheet on phones, side panel on desktop), using Ant Design's `Drawer`, with its placement chosen from the screen width.
- **Not decided yet:** the bottom tab bar (Groups, Friends, Activity, Account) and a redesign of the whole app shell. The top header is on the home page only (ADR-028); the tab bar is a separate decision because it touches every page and needs Friends and Activity to exist.
- **No card on content pages:** the create-group, add-expense and expense-details pages put their content directly on the page, with no card around it; cards stay for list rows on the home page, the loading placeholders and the welcome page. The description and amount fields of the add-expense form were underlined with no fill at first; they are now the standard boxed input (white fill, border, inner radius) like every other input, the amount keeping its 20 px bold text. `ExpenseDetailsCard` was renamed `ExpenseDetails`, since it is no longer a card.
- **Icon on the band:** the group-type icon on the band is bare (40 px, white, no tile, a soft `drop-shadow` so it stands out from the band's own color). The name beside it is centered on it for one line (1 px margin on a 38 px line, against the 40 px icon) and wraps downwards. `GroupTypeIcon`'s `raised` option was removed with the tile. Create group's type tiles are 40 px.

Header buttons are circles; avatars, the profile picture and the header logo are 40 px.
- **Green header, page washes and the group cards (ADR-030 addendum):**
  - **Header:** the home header is an 80 px bar in the theme's primary green with a white 24 px bold name and a 56 px logo. `BrandLogo` draws the wallet of `public/logo.svg` (no longer Ant Design's `WalletOutlined`, which differed from the installed icon); with `onPrimary` it takes the greens sampled from the installed icon on an iPhone (`#149f8b` to `#30ca98`, lighter than the file's, so it does not blend into the bar) and a wallet 1.2 times larger (`ON_PRIMARY_GLYPH_SCALE`).

The home page uses the primary green; Create group and Edit group use `GroupTypeBackground`, which takes the chosen type's wash color (`GROUP_TYPE_WASH_COLORS`: the type's own color, except the trip, whose cyan read green when mixed into a dark page, so it washes with sky blue).

The type options on Create and Edit group sit on a transparent strip, each on a faint white card (6% white in dark mode) 12 px apart, with the chosen one a solid white card (20% white in dark mode, where Ant Design paints the selected item itself).

## ADR-031: Expense data model and split rules
- **Context:** group expenses need per-member shares, several split methods, per-currency balances and later sync and edit history (ADR-010, ADR-012).
- **Decision:** migration 0002 adds two tables, both with a UUID primary key, `updated_at`, `updated_by` and `deleted_at` (ADR-025).
  - `expenses`: `group_id`, `description` (1 to 100), `category` (a stable text key, not a label), `amount_minor` (bigint), `currency` (ISO code), `date`, `notes` (up to 1000), `method` (`equal`, `exact`, `percent`, `shares`, `adjustment`), `created_by`.
  - `expense_shares`: one row per member of the expense, with `paid_minor`, `owed_minor` and `input_value` (what the user typed for the method, so the split can be shown and edited later).
- **Split rules** (`computeShares`, a pure function used by the save function and, for previews and checks, by the form): equal (1 or 0 per member, at least one), exact (minor units adding up to the amount), percent (whole numbers adding up to 100), shares (whole numbers 0 to 1000, at least one in all; parts in proportion), adjustment (extra minor units per member, at most the amount in all; the rest divided equally between every member). Every member gets a share row, with what was entered for them (0 when nothing), so the split can be reopened as entered. The payer must be a member. A split that does not add up comes back as a field error on `split` ("The split no longer adds up."), alongside the other fields' errors.
- **Rounding:** all amounts are integer minor units. When a split leaves a remainder, the payer absorbs it, even when the payer is not part of the split. The user chose this knowingly; it keeps shares summing exactly to the amount.
- **Balances:** computed from the shares, pairwise between members, per currency, never converted. Derived on read, not stored, so edits and sync merges cannot leave them stale. Within one expense each person's net is paid minus owed; those who are short owe those who are ahead (with one payer: everyone else owes the payer their share), a pure function (`debtsOf`, `pairBalances`). The group page shows the user's balance with each other person; the home page shows the user's net per currency (the sum of paid minus owed over their shares, which equals the sum of their pairwise balances).
- **Money formatting:** one shared formatter handles parsing and display for the amount field: "." as the only decimal mark, the currency's decimal places, thousands separators while typing (lakh grouping for INR, western otherwise), maximum 1 billion.
- **Categories:** a fixed list of about 115 in 11 groups (ADR-065), kept in code with stable keys, our own icons (Tabler, ADR-066) and colors (ADR-030: no copied artwork or names). Stored by key so labels can change.
- **Recent currencies:** the group's default first, then the currencies of the user's own latest expenses, up to 3 in all. They are read from the expenses in the account's database (which is per account and on this device), so no separate store is needed. The picker lists the chosen currency on top under "Selected" and leaves it out of Recent and the full list, so each is shown once (the up-to-3 are therefore up to 2 when the chosen one is among them).
- **Pickers:** category, currency, date, payer and split use one shared adaptive dialog (centered on desktop, bottom sheet on phones), the same pattern as the members sheet (ADR-030).
- **Validation:** the expense schema in `schemas.ts` follows ADR-027: Save validates with zod and returns field errors, including "The split no longer adds up". Split rules per method live in pure, unit-tested functions.
- **Delivery:** five phases (simple expense, balances, payer and other split methods, details page, receipt photos), all built in October 2026 (PR #1). Receipts use the `PhotoStore` (ADR-006).
- **Rejected:** storing balances (stale after edits or sync), storing only the final owed amounts without the inputs (the split could not be re-opened), a separate rounding-remainder person (more rows, no benefit).
- **Phase 1 as built:** the service saves an equal split with the user paying (`method` 'equal', `input_value` 1 for each member). The add-expense page is `src/pages/addExpense`; the shared picker is `src/components/AdaptiveDialog`, the category tile `src/components/CategoryIcon` (colors per category group in `src/theme/categoryColors.ts`), the money formatter `src/services/moneyService`. The calendar is `react-day-picker` (MIT, v10; ADR-033), not Ant Design's `Calendar`. `MonthCalendar` (`DateField/MonthCalendar`) holds the shown month itself, draws its own header with Ant Design controls (previous and next arrows, year and month lists; no Month/Year switch) and moves the month with the library's `animate` slide, on a sideways swipe (50 px, more sideways than vertical), on the wheel or trackpad (one month per flick, 350 ms pause; the wheel listener is added by hand as non-passive so the page does not scroll too), or with the arrows. The library has no swipe support of its own. Month names come from `Intl`. Its CSS is themed with Ant Design's CSS variables (`style.module.css`); its own month label is kept for screen readers, hidden with `clip-path` rather than `display: none`, because the old month leaves the page when that label's animation ends. Dates are plain `Date`s (`dateService.fromDay`, `toDay`), so `dayjs` is no longer a direct dependency. A list row says "no balance" when the user paid exactly their own share. The currency list (a few hundred `Intl` lookups) is built once per language and reused.
- **Phase 2 as built:** `expenseService.groupBalances` (the user against each other member, per currency) and `expenseService.balancesByGroup` (the user's net per group and currency, for the home page); the colors of money owed to and by the user are shared in `src/theme/balanceColors.ts`.
- **Phase 3 as built:** the form holds the split as one field (payer, method, numbers per member). The split dialog keeps each tab's entries separately while open, so switching tabs loses nothing; it is mounted afresh on each opening so it starts from the current split, and hidden tabs are unmounted. A live check under the sentence shows "The split no longer adds up" as soon as a new amount breaks the split. The dialog's footer (totals and a Done tick) is a `footer` slot of the shared `AdaptiveDialog`.
- **Phase 4 as built:** `expenseService.getExpense` returns one expense with the shares of everyone who paid or owes; like `getGroup`, it returns null for an unknown, deleted or other group's expense and for a group the user is not in, so the page cannot reveal what exists. The page is `src/pages/expense`. Day formatting (`toDay`, `formatDay`) moved to `src/services/dateService`, shared by the add-expense and details pages. A name taken from an email starts with a capital ("Sam"). On the page, who paid is a grey line under "Added by" (`paidSentence`, one per person with `paid_minor` above 0; not for a settlement), and the split list holds only what each person owes (`owedSentence`, people with `owed_minor` 0 left out); the list's accessible name is "Who owes".
- **Phase 5 as built:** migration 0003 adds `expense_photos` (UUID, `expense_id`, `position`, `mime_type` checked to be `image/…`, `size_bytes`, sync columns); the row's id is the photo's key in the photo store. The `PhotoStore` (`savePhoto`, `getPhoto`, `getThumbnail`, `deletePhoto`) is `photoService.open(accountId)` in `src/services/photoService`, an IndexedDB database per account (`ownledger-photos-<account id>`, ADR-007) with a store for originals and one for thumbnails. Pictures are kept as bytes plus type rather than Blobs, which older Safari cannot store. Thumbnails are JPEGs at most 320 px on the longest side, drawn on a canvas; a picture the browser cannot decode (such as HEIC outside Safari) is its own thumbnail. Saving keeps the photos first and then saves the expense with their rows in one transaction; if the expense is refused or fails, the photos are removed again, so no row points at a missing photo. Pictures are shown through `useObjectUrl`, which shares one `blob:` address per picture and frees it once nothing shows it. Not done yet: asking the browser for persistent storage (ADR-006), and cleaning up photos of deleted expenses (open question).
- **Group switcher (add expense):** the fixed "With you and: All of <group>" chip became a dropdown of the user's groups (`GroupSwitcher`), whole groups only. Choosing one navigates (with `replace`) to that group's add-expense address and carries the entered fields in the router's location state as an `ExpenseDraft` (receipts as `File` objects, which survive structured cloning). `carriedOver` builds the new form's values: the split starts again from the new group's members, and the currency follows the new group's default only if it was still the old group's default. `initialValues` stay the plain defaults, so carried fields count as unsaved input and Back still asks. The page reads its data with `useAsyncData(..., { keepPrevious: true })`: a new key keeps reporting the earlier `ready` data until the new data arrives, instead of `loading`, so switching shows no skeleton; the form is keyed by group id so it starts fresh from the draft. Other pages keep the default (a new key goes back to `loading`). Rejected: only changing the group in place without a new address (the form's members, currency and split all depend on the group and are loaded with it), and letting the user pick people (not wanted).
- **Consequences:** editing an expense rewrites its shares in one transaction. Pairwise balances do not simplify debts across three or more people; that can be added later in the balance query only.

## ADR-032: Hosting on GitHub Pages under /ownledger/
- **Context:** the app is a static client-only site (ADR-001), so any static host will do. The owner already publishes small apps from the GitHub Pages repository `omkarsheral1989/omkarsheral1989.github.io`, where each app has its own folder.
- **Decision:** the app is served at `https://omkarsheral1989.github.io/ownledger/`. `vite.config.ts` sets `base: '/ownledger/'` for development, preview and build alike, so what runs locally has the same addresses as production (`http://localhost:5173/ownledger/`, and `?platform=ios` becomes `/ownledger/?platform=ios`). `BrowserRouter` takes `basename={import.meta.env.BASE_URL}`, so `ROUTES` stays free of the prefix. The PWA manifest's `start_url` and `scope` are the same base, which also gives the service worker the scope `/ownledger/`, so it cannot touch the other apps on the site.
- **Deep links:** GitHub Pages has no single-page-app fallback, so opening or reloading `/ownledger/groups/123` would show its 404 page. `deploy/404.html` is copied to the root of the Pages site (Pages reads 404.html only there). For addresses under `/ownledger/` it redirects to `/ownledger/?/groups/123` (with "&" written as "~and~"), and `restoreRedirectedUrl` (`src/pwa/redirect.ts`, called first in `main.tsx`) puts the original address back before the router starts. Other addresses on the site see a plain "Page not found". Once the service worker is installed, the app's own navigation fallback serves deep links without this detour.
- **Delivery:** `bun run deploy:pages` (`scripts/deploy-pages.sh`) builds, replaces `ownledger/` in the Pages repository with `dist/` and copies `deploy/404.html` to its root. It refuses to run when that repository has uncommitted changes, and it never commits or pushes: that is done by hand there. The Pages repository's location defaults to the folder next to this one and can be set with `PAGES_REPO`.
- **Rejected:** a hash router (`/#/groups/123`: changes every address and the router for a problem the redirect solves), a custom domain at the root (not needed yet), GitHub Actions deploying to the Pages repository (needs a deploy key or token; possible later).
- **Consequences:** every app on `omkarsheral1989.github.io` shares one browser origin, so `localStorage` and IndexedDB are shared with the games there. The app's keys and databases carry an `ownledger` prefix, so a clash is not expected, and a future key must keep the prefix. Google sign-in needs `https://omkarsheral1989.github.io` as an authorized JavaScript origin (origins have no path) once the OAuth client exists. The Google client ID is baked into the build from `.env.local`; it is public by design, but `deploy:pages` builds with whatever that file holds.

## ADR-033: react-day-picker for the date calendar
- **Context:** the date field's calendar (Ant Design's `Calendar`) could not be swiped or scrolled between months and had no animation. Its single value was both the chosen day and the month shown, so the lit day moved with the month and a CSS override was needed to hide it.
- **Decision:** use `react-day-picker` (MIT, React 16.8 or later, depends on `date-fns`). It takes the month shown and the chosen day separately, and its `animate` option slides a month out and the next in. It has no swipe handling, so swiping, wheel scrolling and arrows are our own code (`MonthCalendar`), driving its controlled `month`. The header stays Ant Design (buttons and selects) and the library's CSS uses Ant Design's CSS variables for color and radius. With `prefers-reduced-motion` the slide takes 0 s.
- **Exception to ADR-005:** this is the one place a non-Ant Design component draws UI. Chosen over Ant Design plus a hand-built slide, and over a native `<input type="date">` (native on phones but unstyled, with no swipe or slide in desktop browsers).
- **Consequences:** a new dependency and its `date-fns`. Further calendar changes (a trip-dates range, for example) can use its range mode.
